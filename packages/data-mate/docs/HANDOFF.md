**The cost model: the ROW GROUP is the unit of query cost** — 26-44 us per row group, with **file
count absent from the law**. The decisive pair: 100 files/100 groups and 20 files/100 groups both
answer `count(*)` in **4.1 ms**. DuckDB's default row group is **122,880 rows** and `qpl-search-api`
caps a slice at **100k**, so **no payload can ever fill one**. Never lower `ROW_GROUP_SIZE` on the
producer.

**THE ONE MEMORY CLIFF, precisely bounded.** A **wide top-N** (`SELECT * … ORDER BY … LIMIT`) over
Parquet needs between 512 MiB and 1 GiB and **fails rather than degrading** if it does not get it.
14 of 15 query shapes are fine down to 128 MiB. The law: **threads x row-group x columns projected,
INDEPENDENT of dataset size** — identical threshold at 10M and 100M. A native table survives the same
squeeze because it holds an evictable page cache; a Parquet view caches ~17 MB and has nothing to give
back. **Fix: never emit `SELECT *`.** Also: cap threads (4 suffices at 256 MiB), or budget ~1 GiB per
concurrent wide query.

**`duckdb_memory()` IS NOT RESIDENT MEMORY** — it is elastic buffer-manager residency and equals the
database file size whenever the limit is generous. **Plan with peak process RSS.** See §0.11.

**Also settled:** a `VIEW` over `read_parquet` is identical to inlining it, and a glob to a path
array. Arrow IPC is out (2.1x at 100k rising to 8.1x at 1M, 3.9x the disk); CSV/NDJSON ~17x.

**Still not built:** `deepSelect`/`_skip_if_empty`, stacked `expand_values` (`UNION ALL`), the
date/timezone offset column (unblocked — `icu` is loaded and the idiom is verified), and the remaining
17 functions. **`spatial` must be packaged** before the 13 geo emissions run anywhere but a dev box —
they have **no UDF fallback** (DF7), so those queries fail outright without it.

**Traps that cause silent wrong answers:** `ST_Distance_Sphere` takes (lat, lon); a CHECKPOINT during
concurrent appends does nothing; a macro can shadow a built-in; TIMESTAMPTZ renders in the driver's
zone; RE2 has no lookaround; **`memory_limit` does not bound process RSS** (Parquet's RSS was ~5 GB
under a 1 GiB limit); a generator using `i % N` compresses 2x better than real data.

**Ten defects written up** in `known-defects.md` (DF1, DF2, DF4-DF12 — **there is no DF3**). Three

## 0. THE CORRECTIONS THAT KEEP RECURRING — ITEMS 0 THROUGH 13, READ THEM ALL

**0. THE FLOW. Explained FIVE times. Get this right before touching anything.**

```
qpl-search-api   queries Elasticsearch -> RECORDS. The ONLY place records become a frame
                 (DuckFrame.fromRecords). Sends PARQUET back over the wire.
qpl-worker       WHERE THE TABLE LIVES. Its slicers/fetches query qpl-search-api, each
                 returning a Parquet payload; it ingests the MANY payloads into ONE table
                 representing the entire search query result.
```

**`fromRecords` is NEVER called in qpl-worker.** Multi-slice accumulation is worker-side and
**from Parquet** (`create()` + `append({parquet})`), never from records. A line in NEXT STEPS used to
say the opposite — "`fromRecords` creates a NEW table per call, but the reader fetches in
slices" — inherited from the old engine's `fetchPartialFrames`/`appendAll`; it has been deleted.
**If any doc here contradicts this diagram, this diagram is right.** Do not ask about it again.


Each of these was gotten wrong at least once, several of them three or four times, and every
one cost real work. They are collected here so nobody has to be told again.

**1. This is a NEW ENGINE, not a port.** Corrected 3+ times. Match observable behaviour and the
205 functions; the old engine's internals (`QueryScope`, `JoinChanges`, `Builder.mset`,
`SearchLoader`'s LRU, the per-row correlation in `scope-utils.ts`) are ONE implementation chosen
under `DataFrame`'s constraints and are not a design input. Read `qpl-engine` to extract *what a
query must produce*. Never ask "what does `X.ts` become". Details in §1.

**2. Know the tiers before measuring anything.** Explained 3 times. **api-server** fetches and
produces **Parquet+zstd**; the forked **qpl-worker (~64 GB)** runs the query, including joins.
The wire carries **Parquet, never objects or JSON**. Any join benchmark at 6 GB / 2 CPU is
measuring the wrong tier and is invalid. Diagram in §1 THE BOUNDARIES, envelope in §1 THE
DEPLOYMENT ENVELOPE.

**3. Never inherit a probe's parameters.** `tools/bench/join-shapes.mjs` defaults to `MEM=6GB
THREADS=2`, and reproducing a recorded finding reproduced its wrong premise. Define a benchmark
from the deployment envelope, not from whatever the last script used.

**4. Use the function configs. Do NOT invent a parallel vocabulary.** A `FunctionDefinitionConfig`
already defines name, aliases, `argument_schema`, `accepts`, `output_type`, the implementation,
and `process_mode`, and spaces turns them into **GraphQL directives**, so they are the public
surface. `duckFrameAdapter` exists for exactly this and mirrors `dataFrameAdapter`. A hand-rolled
spec type was built once and deleted.

**5. Explore a package's structure before adding to it.** The DuckDB type mapping was first
dropped in as a one-off `data-types/src/duckdb.ts`; the package defines each FieldType as a
**class in `src/types/v1/`** extending `BaseType`, so it belongs as a fourth method beside
`toESMapping`/`toGraphQL`/`toXlucene`. Likewise the DuckDB adapter belongs in `src/adapters/`
next to the other adapters. Look first.

**6. Put the design in a message BEFORE writing code.** Two substantial pieces were written and
then deleted because the shape was wrong. State the design, name the real choice points, then
build.

**7. Verify how you MEASURE, not just what you measure.** Two false "the process hangs" findings
came from broken detection: `pgrep -f <script>` matches the *enclosing bash process* whose
command line contains the script name, and `kill -0 $pid` succeeds for an unreaped **zombie**.
**Use `wait $pid`** - it reaps and returns a status that cannot lie. When two runs of the same
config disagree, the harness is wrong; stop and fix it before theorising.

**8. A CONFOUNDED AXIS will hand you a confident law with the wrong variable in it.** Added
2026-08-24, and it cost a design rule. Every Parquet sweep varied file count at a fixed total, so
"more files" and "more row groups" moved together in every cell - and the write-up named **files** as
the cause, with a clean ~32 µs constant to back it. The real unit is the **row group**; forcing 100
files to hold 5,000 groups made them 16x slower with the file count untouched.

Three things make this repeatable rather than a one-off:

- **The old table already contained its own refutation.** Under a per-file law every cell in the
  `100 files` column must be equal; 25M cost 12.0 ms against 4.0-4.2 ms for the others, because it
  held 3 groups per file instead of 1. The anomaly was printed, in the same table, and read past. **When
  a column that should be flat is not, that is the finding, not noise.**
- **Name the unit and then try to break the coupling.** The fix was one run holding the suspected
  unit constant while the other variable swept 50x. If two candidate causes cannot be separated by the
  benchmark's own axes, the benchmark cannot support a causal claim yet.
- **Census, do not infer.** The bench now counts row groups with `parquet_file_metadata` before
  measuring. Inferring them from the requested `ROW_GROUP_SIZE` would have been wrong - a small probe
  showed DuckDB rounding 5,000 up to ~6,144, though the real corpus honoured it exactly.

**9. Do not benchmark two things at once.** Ordinary, and still worth writing down: the
`ROW_GROUP_SIZE` runs and the ingest pair were kept strictly serial, because two DuckDB benches sharing
14 cores produce four numbers that are all wrong and none obviously so.

**10. A RATIO IS NOT A RECOMMENDATION. Compute BREAK-EVEN and lead with it.** Added 2026-08-24 after
Jared caught the same error three times in one session: *"this is like the 3rd time you are choosing
the suboptimal and acting like its the optimal."*

**In this system the cost is paid ONCE PER JOB and the benefit is PER QUERY.** A ratio therefore
decides nothing on its own; the deciding number is **Q, the query count** — and §0.0's flow says Q is
small (*"append thousands of times and aggregate rarely"*).

| # | what was recommended | the ratio quoted | what was ignored |
|---|---|---|---|
| 1 | materialise a table | queries 2-20x faster | the job is append-dominated; appends outnumber queries |
| 2 | stitch payloads to >=123k rows | 11x on selective queries | the rewrite cost, and that ~2M is 3x cheaper |
| 3 | consolidate at the realistic slice mix | "~2x, only 4 s" | **break-even was 67 queries** |

- **`extra_one_time_cost / saved_per_query = Q_required`.** Compute it, print it, compare it to real Q.
  If Q is unknown, the recommendation is **undetermined** — say so instead of picking.
- **Seconds against milliseconds must trigger this automatically.** A one-time cost in seconds against
  a per-query gain in milliseconds always needs hundreds of queries.
- **Show the columns break-even derives from** (saved/query, extra cost). Publishing only the derived
  number is how a conclusion survives data that contradicts it.
- **A battery total hides the distribution**: 82% of the 60 ms "saving" was `top 100 rows`; for
  aggregation-shaped work it was 30.5 ms and break-even doubled. Same family as correction 8.


**11. A METRIC THAT TRACKS A FILE SIZE IS NOT MEASURING MEMORY.** Added 2026-08-25, and it produced
a published number that was wrong by 20x. `sum(memory_usage_bytes) FROM duckdb_memory()` was quoted
as "a Parquet view holds 65x less memory than a table". The tell was printed in the same table and
read past: **the native figure equalled the database FILE SIZE to four decimal places at every scale
from 100k to 100M.** It is *elastic buffer-manager residency* — given room DuckDB caches the whole
table, so the metric converges on the file size; squeeze `memory_limit` and the identical workload
completes holding a fraction of it.

- **Peak process RSS is the only honest "will this fit" number.** By it the gap is 3.2x, not 65x.
- **The decisive test for any "memory used" metric is to lower the limit.** If the number does not
  move, it is not resident memory. One run, five minutes.
- Same family as §0.8: a suspicious constant ratio between two columns IS the finding.

**12. "X IS FRAGILE" IS NOT AN ACTIONABLE FINDING. Name the shape, the threshold, and the term it
scales with.** Added 2026-08-25 after Jared pushed back twice on the same paragraph. "A Parquet view
OOMs under pressure where a table survives" was true and useless. Running every query individually
across a limit sweep narrowed it to **one shape of fifteen** (a wide `SELECT * … ORDER BY … LIMIT`),
and two predictions then gave the law: the requirement is **threads x row-group x columns projected,
independent of dataset size**.

- **A blanket claim about a technology is almost always a claim about one query shape.** Find it.
- **Then find what it is proportional to.** "Needs ~1 GiB, fixed" is a capacity line item; "uses a
  lot of memory" is an anxiety.
- The mitigation fell straight out of the law: do not emit `SELECT *`.

**13. RE-CHECK WHETHER YOUR OWN BENCH IS MEASURING THE THING.** Added 2026-08-25. The consolidation
bench timed each target as it built, using `LIMIT n OFFSET k` per batch — which rescans from the
start and is **quadratic in batch count**. It produced non-monotonic nonsense (12.0 s for 82 objects,
3.5 s for 20, 14.6 s for 5) that would have been published as "consolidation cost". **Non-monotonic
output on a monotonic axis means the harness, not the world.** Those numbers were excluded and said
so, rather than dropped quietly.

## 1. The DuckDB work (branch `dataframe-duckdb-refactor`)

### READ THIS BEFORE ANYTHING ELSE — WE ARE BUILDING A NEW QPL ENGINE

**This is a new engine, not a port.** Jared has had to correct this framing more than once, so
it is stated here first:

- **Required:** high-level **feature parity and observable behaviour**. The 205 functions are
  the QPL language and their drift is a public API break. Join semantics, result shapes,
  error behaviour and metrics must match what users see today.
- **NOT required, and actively misleading:** the old engine's internals. `QueryScope`,
  `JoinChanges`, `create-projection-builders`, `Builder.mset`, the per-row correlation in
  `scope-utils.ts`, `SearchLoader`'s LRU, `materialize`'s parent-row loops — all of that is
  **one implementation of those behaviours**, chosen under `DataFrame`'s constraint of having
  no join and no query planner. None of it is a design input.

So when reading `qpl-engine`, extract **what a query must produce**. Do not map old modules
onto new ones, do not ask "what does `X.ts` become", and do not carry its decomposition over.
Every "the old code does it this way, so…" inference in the history below should be read with
suspicion — several were wrong for exactly this reason.

### THE BOUNDARIES — who fetches, who joins, what data-mate owns

```
  Elasticsearch                 ES client returns PARSED JS OBJECTS
        v
  ===== qpl-search-api ==========================  the PRODUCER
  spaces' reader / fetch code    SPACES OWNS: auth, POST bodies, slicing, retries, backpressure
  DuckFrame.fromRecords          coerceToType + typed appender. VALIDATION HAPPENS ONCE, HERE.
  COPY ... (FORMAT PARQUET, COMPRESSION zstd)
  ===============================================
        |   *** THE WIRE CARRIES PARQUET + zstd. *** 22.8 MB / 1M rows.
        |   NOT objects, NOT JSON, NOT dfjson, NEVER gzipped.
        v
  ===== qpl-worker (~64 GB) =====================  the CONSUMER
  MANY payloads, one per fetch   its slicers/fetches each query qpl-search-api
  DuckFrame.create(config)       ONE table for the whole search result
  + append({parquet}) x N        read_parquet: 31 ms/1M, ZERO COERCION
  SQL: join / filter / project / agg    <== JOINS HAPPEN HERE
  ===============================================
```

**`fromRecords` is called ONLY on the api-server, once per ES response. The worker never sees a
record.**

Measured, 1M rows, every option ending at a queryable table on the worker:

| | producer | **worker** | wire |
|---|---|---|---|
| **parquet zstd** | 1,164 ms | **31 ms** | **22.8 MB** |
| ndjson | 803 ms | 248 ms | 194.0 MB |
| ndjson + gzip | 2,665 ms | 385 ms | 35.9 MB |
| dfjson *(today)* | 1,482 ms | 784 ms | 106.3 MB |

The **split matters more than the sum**: the worker is the scarce tier and is 8x cheaper with
Parquet. Settled.

**The strategy, decided:** load the whole dataset, let DuckDB **overflow to disk**, join it all at
once. Not per-row fetches, not key-set batching. A semi-join pushdown may come later — do not
design around it, do not present it as an open question.

### THE STORAGE DESIGN FOR SPACES — what was considered, and what the numbers chose (2026-08-24)

**This is the decision record.** Every option below was measured; tables in `PERFORMANCE.md`. It
exists because the same ground was re-covered three times, each time reaching a different answer.

**The constraints, which are fixed and not design choices:**

- `qpl-search-api` is **stateless and distributed**: one request, **<=100k records**, Parquet over the
  wire. Consecutive slices may hit different instances. **It cannot batch. Ever.**
- Real slices are a **ragged 10k-100k mix**, all **below DuckDB's 122,880-row group**, so **no payload
  can ever fill one row group.**
- `qpl-worker` is the **only stateful component** and **receives every payload's bytes**. It is
  therefore the only place any batching decision can be made.
- The job is **append-dominated and aggregates rarely**. Q (queries per dataset) is SMALL.
- Local disk **may not exist**; S3 may be the only storage.

**The options, and why each was rejected or kept:**

| option | verdict | the number that decided it |
|---|---|---|
| **append each payload into ONE DuckDB table** | **REJECTED** | cost is **per ROW** (~1.88 us/row + ~2.0 ms/statement, corrected 2026-08-25). 258 s to absorb 100M against 6.2 s to land the bytes; break-even **272 queries** |
| **materialise a table at the end** | **conditional** | build is cheap (2.6 s / 20M, cheaper than rewriting Parquet) and queries 2-20x faster — but only pays if Q is large. Not the default |
| **query the payloads directly as Parquet** | **KEPT — the default** | ingest is free; a view is identical to inlining `read_parquet`, and a glob is identical to a path array |
| **consolidate payloads into bigger objects** | **NOT by default** | costs 2-39x a byte copy. Break-even **67 queries** at the realistic mix, 132 for aggregation-shaped work. Only at consistently ~10k slices (break-even **5**) |
| **one single giant object** | **not reachable** | Parquet is immutable, so it can only be built by rewriting everything — and consolidated files already tie it on every real query |
| **Arrow IPC / CSV / NDJSON** | **REJECTED** | Arrow is 30x slower (no row-group statistics, every query full-scans), 16x the size, and loads slower than CSV |
| **native `.db` as the wire format** | **REJECTED** | 4x larger than Parquet+zstd, and zstd is *faster* to load at scale because I/O dominates decode |

**The design, as it stands:**

```
qpl-search-api  ──Parquet+zstd over the wire──>  qpl-worker
                                                  │  persists each payload AS RECEIVED (a byte copy)
                                                  │  no consolidation, no table, no append
                                                  └─ queries them as a view / read_parquet glob
```

**The two switches, and what flips them:**

1. **Consolidate** (buffer to ~2M rows before the FIRST write — never rewrite afterwards) when slices
   are consistently ~10k, or when Q is known to exceed ~50-130.
2. **Materialise** a table when Q is large enough, or when point-lookup queries matter — an ART index
   is 6-8x and Parquet cannot have one at any price.

~~**The one term that could overturn all of this and has NOT been measured: real S3 per-object
request latency.**~~ — **MEASURED (modelled) 2026-08-25, AND THE PREDICTION DID NOT HOLD.**
`bench/report-s3.mjs` puts a known per-request delay in front of minio via `lib/latency-proxy.mjs`.
At 100 ms RTT the request-count model predicts 2.94 s for 87 objects; measured, **133 ms** — the model
over-predicts by ~**22x**, because row-group statistics prune most objects before they are fetched and
the surviving requests are issued **concurrently**. **Latency raises the floor for every layout
equally rather than separating them**; consolidation is worth ~1.2x under latency, not the 8-30x the
zero-RTT numbers implied. Still worth confirming against a REAL bucket under concurrency, but it is
no longer the term that decides the design.

### THE DEPLOYMENT ENVELOPE — measure at the right tier or do not measure

| tier | does | envelope |
|---|---|---|
| `api-server` | serves requests, **fetches**, produces Parquet | small; many concurrent queries per process |
| forked `spaces_qpl_worker` | **runs the query — joins execute HERE** | **~64 GB** |

- **A join benchmark MUST use the worker envelope** (~64 GB, real CPU count). The api-server only
  fetches; benchmarking a join at its size answers nothing.
- **`memory_limit` must be set BELOW the container's cap.** Above it, DuckDB never spills and the
  kernel kills the process — that produced the bogus "OOMs and does not spill" finding.
- **INVALID, DO NOT REUSE:** every number produced at `MEM=6GB THREADS=2`. `tools/bench/
  join-shapes.mjs` now defaults to the worker envelope and prints what it applied.
- Consequence for the join work: with whole-table + file overflow, **any operator that refuses to
  spill is a direct threat**, not an abstract perf note.


**API.**
*Ingest:* `create(config, opts)` + **`append({ records } | { parquet })`** — one method, atomic,
its own connection. `fromRecords`/`fromParquet` are sugar; `fromParquet` also takes a list or glob.
*Query:* `select(exprs, config?, groupBy?)`, `filter`, `join`, `orderBy`, `limit`, `distinct`,
`materialize`, `size`.
*Output:* `rows()`, **`ndjson(opts)`**, **`writeNDJSON(path, opts)`**, `writeParquet`.
*Lifecycle/introspection:* `destroy`, `configureDuckDatabase`, `closeDuckDatabase`, `info()`,
`isMaterialized`, `isOrdered`, `from`, `table`, `columns`. *Escape hatch:* `query(sql)`.

**How it works:** records are coerced by `coerceToType` — the SAME function the regular builder
uses, so parity is by construction — then appended as typed values through a DuckDB appender.
Every query operation composes relations, so a chain is ONE statement in a single pass;
`materialize()` promotes one to a table. Transport is Parquet+zstd.

### BUILT (2026-08-14): `orderBy`, `limit`, `distinct`

**A design I measured my way out of.** I argued `orderBy`/`limit` had to be trailing STATE on the
frame, because nesting `ORDER BY` in a subquery would lose fusion with an outer `LIMIT`. **Wrong —
the optimiser flattens it**: nested and flat produce a byte-identical plan (`TOP_N` + a dynamic
filter in the scan). 5M rows: nested 1 ms, flat 5 ms, unbounded sort 754 ms. So they are ordinary
relation-returning methods, and composition semantics come from SQL for free
(`.orderBy(x).limit(10)` is the top 10; `.limit(10).orderBy(x)` sorts an arbitrary 10).
**Do not reintroduce trailing state.**

**The real hazard is silent order LOSS, and it only appears at scale.** 5M rows / 14 threads,
out-of-order rows from a subquery ending in `ORDER BY x`: projection / `WHERE` / `LIMIT` /
`OFFSET` = **0**; `JOIN` = 303; `GROUP BY` = 2,104; `DISTINCT` = 373. **Both scrambling cases are
perfectly ordered at 20 rows** — so a small test proves nothing. Hence an `ordered` flag on
`Source`, propagated through order-preserving ops, and `join` / aggregating `select` / `distinct`
**throw** rather than discard it.

**`distinct()`** is `SELECT DISTINCT *`, no arguments — `TableDedupNode` carries no fields and the
old engine calls `unique(frame.fields)`. Verified it compares LIST and STRUCT columns and treats
NULLs as equal.

**On limit short-circuiting:** real, but only with the limit IN THE SQL. Unsorted `LIMIT` plans as
`STREAMING_LIMIT` and stops pulling (1 ms vs 68 ms to drain 5M). Sorted plans as `TOP_N`: no early
exit — the top ten are unknown until every row is seen — but a heap of `count` plus a dynamic
filter that skips row groups. Breaking out of `rows()` stops only the JS consumer.

#### WHAT `qpl-engine` ACTUALLY DOES with sort and paging

Checked in the spaces repo, not inferred.

| | where | what |
|---|---|---|
| `params.sort` + `start`/`size` | `v3/execute/search/fetch-from-frame.ts:36-56` | `frame.orderBy(...)`, then paging is an in-memory **`vector.slice`** — NOT an ES `from`, NOT a plan node |
| QPL `orderBy` | `TableOrderByNode` | `frame.orderBy(fields)`, silently SKIPPED when a field is absent (`hasFields`) |
| QPL `limit` | `TableLimitNode` | **`size` ONLY — there is no offset node.** The pipeline truncates; it never pages |

- **Sliced queries REJECT both `sort` and `start`** (`src/search/validation.ts`), so `start` paging
  only ever runs on the small non-sliced API path.
- **`DataFrame.orderBy` parses `'field:asc'` colon strings**, default asc, 400 otherwise, and has
  **no null-placement control**. Engine v2 must translate them — and must QUOTE the field.
- **`limit`'s OFFSET half has no current plan consumer.** Keep it; do not expect a node to emit it.

#### PARITY FIX: null placement follows `DataFrame`, not DuckDB

`Vector.compare` sorts a nil as the **SMALLEST value — nulls FIRST ascending, LAST descending**
(a deliberate fix, per its comment). DuckDB's `default_null_order` is **`NULLS_LAST` for BOTH**.
Since QPL's orderBy node carries no null control, inheriting DuckDB's default would silently move
every null to the other end of an ascending page. So `orderByClause` **always emits direction AND
nulls explicitly**. A bare string spec therefore supplies the EXPRESSION ONLY — `'bytes DESC'`
becomes `bytes DESC ASC NULLS FIRST` and DuckDB rejects it: loud, not quietly divergent.

**Still open — the tiebreaker.** "Non-total ordering" = a sort key with ties. Measured (2M rows,
20 distinct values): the same `ORDER BY bucket LIMIT 10` returned **2 different pages** over 20
runs, and page 1 and page 2 shared **1,305 rows**. `DataFrame` does not have this — `Array#sort`
is stable. **So it is a behaviour regression unless engine v2 appends a unique field** to every
sort. The frame cannot: it cannot know which field is unique.

#### DEFECT FIXED (twice): identifiers were not quoted for reserved words

`quoteIdentifier` skipped anything matching `/^[A-Za-z_][A-Za-z0-9_]*$/` — which **every reserved
word matches**. A field named `group` produced `CREATE TABLE t (name VARCHAR, group VARCHAR)` and
a parser error: **that frame could not be created at all**. The same flaw existed independently in
data-types' `quoteDuckDBIdentifier` for STRUCT members, where `nullObject.inner` produced
`STRUCT(inner VARCHAR)`. Both now quote unconditionally.

**Safe because DuckDB treats a quoted identifier case-INsensitively** (verified) — the opposite of
Postgres. Knock-on: `diffSchema`'s `normalize` strips quotes, since `DESCRIBE` reports members
bare and quoting is rendering, not type.

**The asymmetry, by design:** identifiers WE generate are quoted for the caller; **raw SQL the
caller writes is theirs to quote** — a `group` field needs `filter('"group" = \'y\'')`.

#### BUILT (2026-08-14): JSON export — `writeNDJSON` and `ndjson()`

The final result goes to S3 as **ldjson**. Converting rows to JS objects to get there is the
slowest route and is unnecessary — DuckDB can render the JSON in C++.

**But its native output is NOT DataFrame's**, and shipping it raw would silently change a public
format. Measured against `DataFrame.toJSON` with the options spaces really uses
(`run.ts:174`): `Date` → `"2026-01-10 00:00:00"` not ISO8601; `Long` past `MAX_SAFE_INTEGER` → a
bare number `JSON.parse` ROUNDS, where `DataFrame` emits a string; and **a null field → `"f":
null` where `DataFrame` omits the key entirely**. That last is the big one —
`create-execution-plan.ts:94` defaults `remove_null_fields` to **true** (off only via
`@preserveNullFields`), so 28 keys are emitted where DuckDB emits 30, and **every record with a
nullable field would differ**.

All three are corrected **in SQL before anything is written** (`src/duck-frame/export-json.ts`),
generated from the frame's config: dates via `strftime`, recursively (inside arrays via
`list_transform`, inside nested objects); big ints as strings; nulls via
**`json_merge_patch('{}', ...)`** — RFC 7396 merge-patch deletes nulls and **recurses**. DuckDB
has no `json_strip_nulls`; the filtered-MAP alternative measured 2.6x slower. **CORRECTED 2026-08-17 — the 72 ms / ~7M rows/s figure was wrong for a real row.** Re-measured
on the 30-field benchmark corpus: **540 ms / 500k (~925k rows/s, 402 MB of JSON)**. The cost
scales with row WIDTH — 3 fields is 37 ms (13.5M rows/s), 20 fields is 246 ms (2.0M rows/s) —
so 72 ms is only reachable on a ~5-field row and must never be quoted as the export's cost.
DuckDB's own uncorrected `to_json(row)` is 167 ms, so the whole corrected projection is 3.2x
raw, and still ~6x faster end to end than `DataFrame` + `JSON.stringify`.

Two methods, same projection, identical bytes: **`writeNDJSON(path)`** (whole file) and
**`ndjson()`** (streamed, so a caller can flush to S3 as it goes and never hold the result).
Accuracy is pinned against `DataFrame` ITSELF in `test/duck-frame/export-json-spec.ts` — 20
fields, both null modes.

> Trap: forcing this with `count(*)` reported 500k rows in **0 ms at 1.5 billion rows/s** — the
> optimiser discarded the projection, so no JSON was built. `sum(strlen(...))` forces it.

#### FIXED 2026-08-17: JSON number rendering now matches `JSON.stringify`

**Found by exporting the 30-field BENCHMARK corpus** rather than the spec's 2-record fixture,
whose floats (`0.25`, `1.5`) are all fractional: **57 of 500 lines differed in bytes.** Four
divergences, all in `export-json.ts`, all of the same class as the three it already corrected:

| | `DataFrame` | DuckDB was | now |
|---|---|---|---|
| integral `Float`/`Double`/`Number`/`Vector` | `5` | `5.0` | `5` |
| `GeoPoint`/`Geo`/`Boundary` on whole degrees | `{"lat":-90}` | `{"lat":-90.0}` | matches |
| `-0` | `0` | `-0.0` | `0` |
| **non-finite** | `null` | **`Infinity`** | `null`-ish, see below |
| big `Long` **inside an array** | a STRING | a bare number | a STRING |

**The non-finite one was not cosmetic:** DuckDB wrote a bare `Infinity`/`NaN` token that
`JSON.parse` REJECTS, so one infinite value made an exported line unreadable. Both engines accept
`Infinity` through coercion, and a QPL divide-by-zero reaches it, so this was live.

**Cost, measured (the condition Jared set): +37 ms on 500k rows, 7.3%** over the previous
projection (504 -> 540 ms). Accepted.

**Two residues remain, both narrow, both pinned as tests:**
1. **`abs(x) >= 1e21` writes `1e21` where JS writes `1e+21`.** Not fixable through the JSON type,
   which re-normalises any number given to it (`CAST('1e+21' AS JSON)` renders back as `1e21`);
   fixing it means assembling the object as raw text and losing `json_merge_patch`. Negative
   exponents already agree — they carry their sign.
2. **A non-finite value loses its KEY in the default mode.** It becomes SQL NULL, and RFC 7396
   merge-patch uses null as the delete sentinel, so there is no null that survives stripping.
   `DataFrame` writes `"v":null`. Byte-identical under `@preserveNullFields`; both are valid JSON
   and mean the same thing.

Now **500/500 lines byte-identical** on the benchmark corpus.

#### DATE + TIMEZONE: re-investigated AND the defect FIXED, 2026-08-17

The previous entry said the corruption was in the **UDF Date RETURN** path and that `formatDate`
**matched**. Both are false. Re-measured across `TZ=UTC`, `America/New_York` and `Asia/Tokyo`.

**THE BUG (a plain defect, not a design gap).** `DuckDBTimestampValue.toString()` is
`'2026-08-14 01:02:03.456'` — space-separated and **zone-less**. `createScalarFunction` passes the
raw wrapper straight to the JS function, every date primitive coerces it by stringifying, and
`new Date('2026-08-14 01:02:03.456')` parses a zone-less string as **MACHINE-LOCAL**. So every
date UDF's INPUT drifts by the host's UTC offset:

| TZ | drift |
|---|---|
| UTC | 0 — **which is why it looked fine** |
| America/New_York | +4 h |
| Asia/Tokyo | −9 h |

`Date.parse(String(v) + 'Z')` gives the right millis, proving it is only the missing designator.

**It is far wider than "the timezone functions".** It corrupts the input of EVERY date function,
whatever it returns — measured under New York, 13 of 16 diverge:

| output | e.g. | DataFrame | DuckFrame |
|---|---|---|---|
| String | `formatDate` | `2026-08-14 01:02:03` | `2026-08-14 05:02:03` |
| Number | `getUTCHours` | `1` | `5` |
| Date | `addToDate(hours:3)` | `04:02:03Z` | `08:02:03Z` |
| Boolean | `isBefore('03:00Z')` | true | **false** |

`isAfter`, `isBefore` and `isBetween` all **flip** between `TZ=UTC` and `TZ=America/New_York` on
identical data and an identical query. `DataFrame` is machine-INdependent (it carries the offset in
its tuple); DuckFrame currently is not.

**FIXED.** `makeInputConverter(type)` in `duck-values.ts` — the mirror of `makeValueConverter` —
and `createScalarFunction` now applies it, keyed off `spec.parameter`. For `FieldType.Date` the
function is handed `Number(value.micros / 1000n)`: epoch millis as a plain number, which is what
`DateVector` itself holds, what `toEpochMSOrThrow` returns untouched, and costs no parse per row.
The same numeric conversion `toPlainValue` already made for `rows()`. Everything else passes
through. The structural hole was that the output side had `makeValueConverter` while the input
side had **no conversion at all**.

**Verified after the fix:** all 7 date validations agree with the primitive under BOTH `TZ=UTC` and
`TZ=America/New_York`, and `isAfter`/`isBefore`/`isBetween` now return the **same** answer under
both (they used to flip). `formatDate`, `getHours`, `getUTCHours`, `addToDate`, `toHourlyDate`,
`toDate` all match `DataFrame` under New York. The blast radius went 13-of-16 differing to 2, and
those 2 are the offset-display question below.

**Regression-guarded** in `test/duck-frame/date-udf-spec.ts` (11 tests). The guard that matters
asserts the JS **type and value** the function receives, because jest caches `TZ` at VM startup so
a test cannot switch it, and under `TZ=UTC` the drift is zero — an "is the answer right" test would
pass on a UTC CI box either way. Reverting the one-line wiring fails 2 tests **under UTC**,
checked.

**Date is the ONLY type this hurts.** Measured, what a UDF receives per column type: `Long` →
`BigInt`, `IP`/`Keyword`/`Text` → `String`, `Double`/`Float`/`Number` → `Number`, `Boolean` →
`Boolean`, an array element → the unwrapped scalar. All fine. `GeoPoint` **throws at
registration** (`duckDBTypeObject` refuses STRUCT) — loud, so not a silent risk. Only `Date` gives
a wrong answer quietly.

**A pre-existing hazard this exposed, in BOTH engines:** `isFriday`/`isThursday` and friends are
locale-sensitive by design — `DataFrame`'s own answer changes with the host timezone (measured:
`isFriday` keeps the row under `TZ=UTC` and nulls it under `America/New_York`, because 01:02Z on
the 14th is Thursday evening in New York). DuckFrame now matches that exactly, so this is parity,
not a gap — but it means QPL day-of-week results already depend on the worker's TZ today. Pin the
worker's timezone if reproducibility matters.

**NOT affected: the non-UDF path.** Ingest → storage → SQL (`date_trunc`) → ldjson export is
**byte-identical under UTC, New York and Tokyo** (verified). Ingest stores epoch millis and the
export uses `strftime` on a naive TIMESTAMP, neither of which reads a timezone.

**Related hardening: the DuckDB session timezone is NEVER pinned.** `configureDuckDatabase` sets
`temp_directory`, `max_temp_directory_size`, `memory_limit` and `threads` — not `TimeZone`, so
`current_setting('TimeZone')` follows the host. Nothing in the current path reads it, but ICU **is
loaded**, and `timezone(zone, ts)` renders in the SESSION zone — so `SET TimeZone='UTC'` becomes
mandatory the moment any timezone work moves into SQL.

#### STILL OPEN: the offset question, which is SEPARATE from the defect above

Even with the bug fixed, `setTimezone`/`toTimeZone`/`toTimeZoneUsingLocation` return a
`DateTuple [millis, offsetMinutes]` and `toTimestamp` keeps **only the millis**. So:

| | `DataFrame` | `DuckFrame` |
|---|---|---|
| `setTimezone({timezone: 120})` | `2026-08-14T03:02:03.456+02:00` | `2026-08-14T01:02:03.456Z` |

**Those are the SAME INSTANT** — nothing is lost but the display zone. The old entry called this
value corruption; it is not. What IS lost is the user's directive: `@setTimezone` appears to do
nothing.

Options, now better informed:

1. **Render it in SQL. Measured to work, exactly.**
   `strftime(ts + INTERVAL 120 MINUTE, '%Y-%m-%dT%H:%M:%S.%g') || '+02:00'` produces
   `2026-08-14T03:02:03.456+02:00` — **byte-identical to `DataFrame`**, no UDF, no storage. Works
   because a numeric `setTimezone` offset is a CONSTANT for the column, so it can live in the
   output field config rather than in a row. Best option for `setTimezone`.
2. **`output_type` -> String**, the way `formatDate` already escapes this. Exact output parity for
   all three functions. Cost: the field stops being a Date, so a later sort is lexicographic
   rather than by instant — wrong across mixed offsets.
3. **A companion offset column** (`created` + `created__offset`). Preserves both instant and
   offset, and is the only option that handles `toTimeZoneUsingLocation`, whose offset is genuinely
   per-row. Cost: every projection must thread the second column through.
4. **STRUCT{millis, offset}** — rejected: it changes the Date column type, so every SQL date
   function, comparison and ORDER BY would have to unwrap `.millis`.
5. **TIMESTAMPTZ** — rejected, as before: it renders in a SESSION zone, not a per-value offset.

Note for 1 and 2: `toTimeZone('America/New_York')`'s offset is **not** constant — it depends on
each row's date (EDT vs EST). DuckDB can compute that natively with ICU, which makes it a case for
the SQL-vs-UDF dispatch descriptor rather than a UDF.

#### 0. PACKAGE `inet` AND `spatial` INTO THE WORKER IMAGE — a build step, not a blocker

**An earlier version of this section called this a blocker. It is not, and Jared was right to push
back.** Packaging a DuckDB with extensions is routine. Measured 2026-08-19, with an empty extension
directory and no install step:

```sql
LOAD '/path/to/inet.duckdb_extension';   -- succeeds, install_mode stays NOT_INSTALLED
SELECT TRY_CAST('1.2.3.4' AS INET);      -- works immediately
```

`LOAD` takes a plain file path, and `extension_directory` is a create-time option
(`DuckDBInstance.create(':memory:', { extension_directory: '/opt/duckdb-extensions' })`). So: run
`INSTALL inet;` at image build time into a baked directory, or `COPY` the `.duckdb_extension` file
in and `LOAD` it by path. Where the worker has network, the existing autoload already works and
nothing is needed at all.

The one deliberate choice: **`LOAD` at bootstrap rather than on first use**, so a missing extension
fails at startup instead of mid-query. `DuckFrame` has no extension handling today; that is the
work.

**`spatial` is the same job but bigger and now REQUIRED**, because 13 geo functions are promoted and
none of them has a UDF path to fall back to (DF7) - without the extension those queries fail
outright rather than running slowly:

| | `inet` | `spatial` |
|---|---|---|
| size | 5.2 MB | **57 MB** |
| autoloads? | yes | **NO** - `Catalog Error: ... st_point is not in the catalog` |
| functions it unlocks | 20 IP | 13 geo |

Both are keyed by DuckDB version AND platform (`v1.5.5/osx_arm64` here, `linux_amd64` in prod), so a
`@duckdb/node-api` bump silently invalidates a baked file and `LOAD` falls back to the network.
Drive the fetch from the installed version, or pin it. `INSTALL <name> FROM '<local-dir>'` also
works offline - verified against a plain gzipped directory - if a private mirror is preferred.

Right now `LOAD spatial` happens only in `sql-emission-spec.ts`'s `beforeAll`, as test setup.

**A) Genuine walls (4)**

| function | why, verified |
|---|---|

**THE 28 MB/MILLION IN `PERFORMANCE.md` IS A GENERATOR ARTEFACT, NOT A PROPERTY OF THE DATA.**
These fixtures measure **~106 MB/million** — 3.8x larger. The recorded figure came from a
generator built on `i % N` and linear sequences, and §DO NOT already noted that such a generator
compresses ~2x better than real data. **The tell was printed in the report's own table:** 29.21,
28.14, 28.11, 28.02, 28.01 MB/million across a **1000x** range of scales. A compression ratio that
constant means every row is equally novel — what a periodic generator produces and real data never
does. Same family as §0.8 and §0.11: *a suspiciously constant number between two columns IS the
finding.* **Any size or throughput figure derived from the old corpus is optimistic by roughly
4x.** Query TIMINGS are less affected, but the I/O-bound shapes are.

**PARQUET DICTIONARIES ARE SCOPED TO THE ROW GROUP, NOT THE FILE** (measured, one VARCHAR column
over 1M rows): 100 distinct values costs 0.9 bytes/row, 122,880 (one row group) costs 4.0, and
1,000,000 costs only 4.3. Nearly all the compression benefit is consumed by the time cardinality
reaches the row-group size. That is why bytes/row is flat across scales for **both** generators,
and why dropping `email` from 1e9 to 2e6 distinct changed the total by under 8%. **Raw cardinality
is the wrong lever; row-level LOCALITY is the right one.**

**The selectivity check caught a real defect on its first run:** `email LIKE 'user1%'` measured
**55.6%** against an intended 10%, because with a variable-width number the range
1,000,000-1,999,999 is half the values on its own. Fixed-width zero-padded digits over a full
decade make the leading digit uniform. `inspect-fixture.mjs` re-checks all five battery predicates,
and they must stay stable across regenerations or the benchmark quietly changes meaning.

**The generated files live in `~/fixtures/qpl/`** — outside any git repo, on a durable volume
rather than `/private/tmp` (which macOS purges on reboot). 100M and 1B are there and verified; that

**Layout:** one bucket, prefix per scale, versioned — `s3://<bucket>/v1/<scale>/`. A flat bucket is
a **correctness hazard**, not untidy: `S3_GLOB` defaults to `**/*.parquet`, which would match every

#### MULTI-SLICE INGEST — BUILT 2026-08-14

Accumulation is **worker-side, from Parquet** — see §0.0 for the flow.

Jared rejected the first API (`DuckFrame.empty()` + `appendParquet()`): *"why do I need to declare
`DuckFrame.empty`? Isn't a brand new DuckFrame already empty? Why two methods just to add data?
The frame should know if the table/view it represents is live and be in charge of it."* All three
right. What is there now:

- **`DuckFrame.create(config, opts)`** — a new frame, owning a table, empty. There is no `empty()`.
- **`frame.append(source, opts?)`** — **ONE method**: `append({ records })` on the api-server,
  `append({ parquet })` on the worker. Returns rows added. `fromRecords`/`fromParquet` are now
  create+append, so there is a single ingest path.
- **The frame owns its storage:** appending to a relation **promotes it to a table in place**, so
  a caller need not know which it holds. That is the only mutation of `this`.
- **Appends are ATOMIC.** Verified: a DuckDB appender participates in the connection's
  transaction, so ROLLBACK removes rows it had already flushed. A bad payload cannot corrupt
  payloads already assembled.
- **`INSERT ... BY NAME`, not positional** — measured: a plain `INSERT ... SELECT *` FAILS when a
  payload's column order differs, and separate api-server responses cannot be trusted to agree.
- **`AppendError`** says what SURVIVED: `appending 1 record(s) to table "x" failed - it was rolled
  back, so the table is unchanged and still has 4 row(s). Cause: ...`. `rowsRemaining` is counted
  after the rollback and only on the failure path. `fromRecords` deliberately does NOT wrap — it
  is one-shot, nothing survives, and its contract is to throw what `DataFrame` throws.
- **`frame.info()`** — `{ name?, kind, isMaterialized, isOrdered, database, columns, rows, sql,
  appends }`, counting SUCCESSFUL appends only.

Appending is the ONE place a table legitimately grows; the DO-NOT-mutate rule holds everywhere
else, because relations read the table by name. Append while assembling, derive after.
Spec: `test/duck-frame/multi-parquet-spec.ts`, 23 tests.

#### CONCURRENT APPENDS — the bug, and the numbers

Jared asked how `append` behaves with several fetchers on one frame. **It did not work at all.**
`BEGIN`/`COMMIT` ran on the process-wide SHARED connection, but a DuckDB transaction belongs to a
CONNECTION. Measured: a second concurrent `BEGIN` throws `cannot start a transaction within a
transaction`; that append's `ROLLBACK` then discards the FIRST append's rows; and the connection
is left poisoned - every later statement, for any frame, fails with `Current transaction is
aborted`.

**Fix: every `append` takes its own connection.** Regression-verified by reverting it: 5 of 23
tests fail. Concurrency is then safe and faster - 10 concurrent appends into the same table from
10 connections all succeed, no write conflict.

**Throughput, 1M rows / 20 payloads** (`tools/bench/append-ingest.mjs`; darwin, 14 CPU):

| | time | rate |
|---|---|---|
| producer: `fromRecords` + `writeParquet` | 1,137-1,194 ms | ~850k rows/s, **2.1 MB wire** |
| worker: sequential `append` x20 | ~350 ms | ~2.9M rows/s |
| worker: CONCURRENT `append` x20 | **118-145 ms** | ~7-8.5M rows/s |
| worker: ONE `append`, all 20 paths | **78-90 ms** | ~12M rows/s |
| records `append`, 200k rows | ~195 ms | ~1M rows/s |

**Worker ingest is 7-30% of producer cost** - it is not the bottleneck. Coercion is the expensive
half and happens ONCE, on the producer. Transaction overhead is negligible, so atomicity is free.
Batching paths into one `append` is ~4x a sequential loop.

> test` (swc, module registry, coverage). An earlier version of this table said 205k rows/s for
> the producer; standalone it is ~850k. Correction §0.7, earned again.

#### CORRECTION: `expand_values` with `corelate_values_across_fields: false` is NOT a cross product

I claimed it was, from the interface comment plus a DuckDB probe, **without reading the
implementation**. Wrong. `expand-values.ts` decides it in `calculateSize`:

| flag | rows per input row | shape |
|---|---|---|
| `true` (search / `qpl_context`) | `max(len)` | **positional zip**, short lists NULL-padded — exactly several `unnest()`s in ONE select |
| `false` (`@expandValues` on individual fields) | **`sum(len)`** | **stacked**: each field expands into its OWN block of rows, the others NULL there |

So `false` is vertical concatenation, not a product — `['a','b','c']` + `[1,2]` gives **5** rows,
not 6. In SQL that is `UNION ALL` of one projection per field. **No FROM-clause extension is
needed; that earlier claim is withdrawn.**

**Parity detail:** when every expanded list is empty, `calculateSize` forces the count to 1, so
**the row SURVIVES with nulls**. A plain DuckDB `unnest` DROPS rows whose list is `[]`/NULL. The
fix that works: `unnest(CASE WHEN x IS NULL OR len(x) = 0 THEN [NULL] ELSE x END)`.

#### `DuckContext`: DONE (2026-08-13)

`DuckContext` is **not exported**. Databases are cached per path behind an internal
`getContext(database?)`; `closeDuckDatabase(database?)` is the teardown. `frame.query(sql)`
replaced the old `get context()` — it hands out neither connection nor instance, so it cannot
route frames between databases.

`configureDuckDatabase({ database, tempDirectory, maxTempDirectorySize, memoryLimit, threads })`
— all runtime `SET`s, so it reconfigures an open database. **`tempDirectory` is what makes
whole-dataset-plus-overflow work**: without it an over-limit query fails instead of spilling.

**Traps, measured:**
- **Only the exact string `:memory:` is in-memory.** A bare name AND the `:memory:<name>` form
  each write a database FILE into the working directory. Tests need no `database` option — jest
  gives each test file its own module registry.
- **`frame.query()` is JSON-rendered**, so a BIGINT returns as `'2'`, not `2n`. `rows()` is the
  native-value path.
- **DuckDB reads `'2GB'` as 2x10^9 bytes** and reports `1.8 GiB`. Use binary units.
- `DataType.toDuckDB()` lives in data-types, one `toDuckDB()` per FieldType class beside
  `toESMapping`/`toGraphQL`/`toXlucene`. It is **deeper than its siblings**: `getGroupedFields`
  splits on the first dot only, so `GroupType.toDuckDB()` regroups and recurses — otherwise a
  nested object emits a STRUCT with a dotted member name, a broken table definition.
  **Rebuild data-types after touching it**; data-mate resolves it to `dist`.

#### `DuckContext`: what survived from the planning

The original plan and its long justification are deleted - the work is done. Three things from it
still matter:

- **A bad argument not to repeat:** *"cross-frame joins need both tables in one catalogue, so the

- **The connection rule, MEASURED:** DuckDB concurrency is fine - many connections per instance,

### THE 205 FUNCTIONS ARE GQL DIRECTIVES THE USER TYPES

Not just "the QPL language" in the abstract - **the transform and validation function configs
are turned into GraphQL directives that a spaces-UI user puts on a field**, and that is the
instruction to run that function in the transform pipeline.
`qpl-engine/src/v3/type-defs/directives.ts` walks `functionConfigRepository`, filters by

need an *enum*, but v2 must still map those directive names onto SQL, and renaming one is a

### UDFs: vectorized, and three facts they rest on

1. **Registration is INSTANCE-wide, not connection-scoped.** A function registered on one
   connection is visible to every other, including the private one each `rows()` stream opens.
   Without this, UDFs and streaming would be incompatible.
2. **DuckDB DOES call a UDF with NULL arguments**; data-mate never does. So the wrapper **skips
   nulls by default**, and `callWithNull: true` opts back in. Without that, behaviour diverges on
   every nullable column.
3. **Two type mappings exist and must agree.** `DataType.toDuckDB()` gives type STRINGS for DDL
   and lives in data-types; registration needs the binding's type OBJECTS, and data-types must
   not depend on `@duckdb/node-api`. So `scalar-function.ts` carries the object map, and
   `duckDBTypeObject` **throws** for STRUCT and JSON types rather than guessing. `diffSchema` is
   what catches the two maps drifting.

**A registered UDF requires `instance.closeSync()` or the process never exits** —
`disconnectSync()` alone is not enough, and `destroySync()` on the function makes no difference.
Invisible until UDFs land, which is exactly when it is hardest to diagnose.

Cost: **superseded 2026-08-18** - the old "~4.5-10x a trivial native cast" figure was measured on one
column of an uncompressed in-memory table, which is the worst case on both axes. See §THE 2026-08-18
MEASUREMENTS for what it actually costs (178 ns/value of pure marshalling, single-threaded, but once
per DISTINCT value after a checkpoint). The same docstring appears in `scalar-function.ts` and should
be corrected there too.

### BUILT (2026-08-13): groupBy, join, and the adapter

- **`select(expressions, config?, groupBy?)`** — a `GROUP BY` appended to the projection it
  already builds. Grouping takes raw expressions, so `date_trunc('day', created)` is fine;
  `having` is `.filter()` on the result.
- **`join(other, { on, select, config, type?, as?, otherAs?, groupBy? })`** — both sides aliased,
  because frames routinely share column names and a subquery in FROM needs a name. **N-way joins
  chain** and stay ONE statement (tested to 4 levels); friction is that a column needed at level 4
  must be projected through every level.
- **`duckFrameAdapter(fnConfig, { field, inputConfig, args? })`** — the DuckDB sibling of
  `dataFrameAdapter`, returning `{ expression, outputConfig, functionName }`.

**DO NOT hand-write a UDF spec.** The function configs already ARE the definition — name,
aliases, `argument_schema`, `accepts`, `output_type`, the implementation, `process_mode` — and
spaces turns them into GraphQL directives. A parallel spec type was built once and deleted.

Adapter decisions mirror `dataFrameAdapter` deliberately: args bound once via `create()`
(**per-row args unsupported** — a UDF's inputs are columns); result type from the function's own
`output_type`; `ProcessMode.NONE` emits the bare column; `INDIVIDUAL_VALUES` on an array column
becomes `list_transform(col, x -> udf(x))`; validations emit
`CASE WHEN pred THEN col ELSE NULL END`; an `accepts` mismatch **throws** for a transform and
**NULLs** for a validation — the same asymmetry as the JS adapter.

**Two defects found by driving real configs through it:** a UDF's JS result must go through
`makeValueConverter` (a `number` into a BIGINT vector throws), and `rows()` leaked DuckDB value
wrappers (`DuckDBListValue`, struct wrappers, bigints that `JSON.stringify` refuses) — fixed with
`toPlainValue`, since `rows()` is the OUTPUT path.

### FAILURE CONTRACT: matches `DataFrame` (settled 2026-08-14)

Jared's call: behave like `DataFrame` unless there is a reason not to. There wasn't one.

- **Strict mode (the default) fails FAST on the first bad value.** `DataFrame`'s Builder throws
  out of `valueFrom` and nothing catches it, so a bad batch costs one value's work. The old code
  collected every failure first for a richer message - same outcome, but a full pass over a
  doomed ingest to get it. Parity won.
- **A failed ingest leaves NO table behind.** The table is created before the append loop, so
  throwing out of it used to orphan a fully-populated table that **no caller could reach** - no
  frame was returned, so nothing could `destroy()` it. `DataFrame.fromJSON` leaves no artifact.
  Now dropped before rethrowing. That was a resource leak, not just a parity nit.
- **`mode: 'lenient'` stays** as the opt-in extra: nulls the value, collects every failing field
  with counts and examples. It is the hook for situationally continuing rather than failing the
  batch, and the one place the full pass earns its cost.
- Already matching, unchanged: validations null the value and keep the row
  (`CASE WHEN pred THEN col ELSE NULL END`), and a throwing transform aborts the whole query
  because the error propagates out of the UDF - exactly as it does in `DataFrame`.

### CONCURRENCY: measured, the shared connection is fine for everything except streams

Jared's expected workload is several `DuckFrame`s ingesting from search **at the same time**
into different tables. Probed (`scratchpad/concurrent-ingest.mjs`, `shared-conn-risks.mjs`),
4 tables x 20k rows:

| case | result |
|---|---|
| concurrent ingest, 4 tables, ONE shared connection | **OK** - all counts and distinct values intact |
| concurrent ingest, one connection each | OK |
| ingest while a stream runs (separate connections) | OK, stream not truncated |
| one ingest THROWS mid-flight while another runs on the same connection | **OK** - no collateral damage, the good one completes |
| query on the shared connection while an appender is open | **OK** - sees flushed rows, loses none |
| two appenders on the SAME table, one connection | **OK** - 40k rows |

**So appenders and queries share a connection safely.** The only per-connection hazard is an
open *streaming result*, which is why `rows()` - and only `rows()` - takes its own connection.

### HOW TRANSFORMS AND VALIDATIONS WORK — the machinery to reproduce

Sources: `src/adapters/data-frame-adapter/index.ts`, `src/builder/Builder.ts`,
`src/column/utils.ts`, `qpl-engine`'s `run-pipeline/operations/column-nodes/index.ts`.

```
Column(vector, configA)
  -> fnDef.output_type(configA, args) = configB   <-- THE TYPE CHANGES HERE, mid-plan
  -> Builder for configB
  -> for each value: builder.set(fn(value))       <-- the Builder ENFORCES configB
  -> Column(newVector, configB)
```

**The three things that matter:**

1. **`output_type` changes the field config mid-plan**, and the Builder for the NEW config is what
   coerces the result. That is why `duckFrameAdapter` returns `outputConfig` — thread it into the
   next step.
2. **Validations NULL the value and keep the row.** Transforms THROW, aborting the query.
3. **A transform sees non-nil values only** (`ReadableData` yields non-nil), unless the function
   opts into nulls. This is the source of the UDF null-skipping rule above.

### Aggregation — the lesson from the false start

Aggregation is `select(expressions, config, groupBy)`, built and shipped. The false start worth
not repeating: a separate `AggregationFrame`-style surface was built first, then deleted, because
an aggregate in SQL is **a projection with a GROUP BY** and composes with everything else. Do not
give it its own execution concept.

### INGEST COST, MEASURED 2026-08-17 — and the bulk-buffer path is NOT worth pursuing

`tools/bench/ingest-breakdown.mjs`. 500k rows x 30 columns, phases split:

| | time | share |
|---|---|---|
| `coerceToType` only — **BOTH engines pay this** | 1,232 ms | 42% of DuckFrame, 58% of DataFrame |
| `DataFrame.fromJSON` (coerce + JS vectors) | 2,140 ms | |
| `DuckFrame.fromRecords` (coerce + convert + append) | 2,931 ms | |

So the addressable gap is **791 ms**, and coercion — shared, identical code — is the single
largest component of both. A perfect ingest could not beat 1,232 ms.

**Per field type (500k, one column each), DuckFrame / DataFrame:**

| at parity or better | ~1.2x | **the losses** |
|---|---|---|
| **Date 0.86x**, Date-as-ISO 0.94x, Boolean 0.95x, Short 0.98x | Long 1.19x, Date[] 1.19x, Double 1.21x, Integer 1.23x, IP 1.34x | **Keyword 3.45x**, **Keyword[] 3.34x**, GeoPoint 1.88x, Integer[] 1.55x |

**This kills the optimisation I was about to recommend.** The bulk-buffer path
(`vector_get_data`/`copy_data_to_vector`, confirmed present in `@duckdb/node-bindings` — NOT in
`node-api`, whose typed vectors expose only `getItem`/`setItem`) works **only for fixed-width
types** — and every fixed-width type is ALREADY at 0.86-1.23x. The types that actually lose are
exactly the ones a raw buffer cannot touch: VARCHAR and nested LIST/STRUCT. Do not spend on it.

**Two predictions of mine that the numbers refuted**, recorded so they are not repeated:
`BigInt()` per value for Integer/Long, and `BigInt(millis) * 1000n` for Date, were supposed to
dominate. They do not — those types are ~1.2x and Date is FASTER than `DataFrame`.

**Why strings cost what they do, and why it is not fixable.** `makeValueConverter` for a Keyword
is the identity function — there is no wrapper to remove. The time is inside the binding:
every JS string must be transcoded from UTF-16 to UTF-8 and copied into DuckDB's string heap,
where `DataFrame` merely keeps the JS string reference. That is the price of the data being in
DuckDB at all, it is paid ONCE on the api-server (the tier with headroom), and it buys 23x on
serialize-to-wire and 34x on the worker's read.

**If absolute ingest speed ever matters, `coerceToType` is the target** — 42-58% of the time,
and the same code on both sides. Not a parity issue, so it does not affect any comparison.

### THE CHECKPOINT, MEASURED PROPERLY (2026-08-19) — cost, and the two traps that came first

The 2026-08-18 sections below say "checkpoint the master table, ~200 ms per 1M rows". That was one
measurement at one size, taken through a call that turns out to decline silently at some sizes, on a
database that was checkpointing behind our back. All three had to be fixed before a cost curve meant
anything. **Nothing below contradicts the finding that a checkpoint is worth taking - it makes the
cost smaller and the mechanism knowable.**

#### 1. A plain `CHECKPOINT` after the ingest path SILENTLY DOES NOTHING

Deterministic at 1M and 2M rows over 20 Parquet appends: `CHECKPOINT` returns in **0 ms** with all
2,682 segments still `Uncompressed` and memory unchanged. **`FORCE CHECKPOINT` behaves identically.**
Neither errors. Other sizes worked, which is what makes it dangerous - it looks like a cheap
checkpoint, not a skipped one.

This is **not** only the concurrent-append case the old notes describe. These appends were sequential
and fully awaited.

| action taken after the appends | then `CHECKPOINT` |
|---|---|
| nothing | 0 ms, **no-op** |
| wait (polled for 2 s) | 0 ms, **no-op** |
| `SELECT 1` | 0 ms, **no-op** |
| read the table (`count(*)`) | 0 ms, **no-op** |
| `BEGIN TRANSACTION; COMMIT` | 0 ms, **no-op** |
| `DELETE ... WHERE false` | 0 ms, **no-op** |
| **another `append()`** | **145 ms, 2,682 -> 11 uncompressed** |
| **a one-row `INSERT`** | **134 ms, 2,682 -> 17** |
| **`CREATE TABLE _x(a INT)` + `DROP TABLE _x`** | **132 ms, 2,682 -> 10** |

So it takes a real WRITE since the last checkpoint to arm it, and reads/waits/empty transactions do
not count. Evidence: `tools/probe/checkpoint-noop.mjs` (which also rules out our own code - the same
shapes in raw SQL against the binding never no-op), `tools/bench/checkpoint-cost.mjs`.

**Therefore a `frame.checkpoint()` must arm AND verify.** Arm with the throwaway
`CREATE TABLE`/`DROP TABLE` (it costs 0 ms), then check
`SELECT count(*) FROM pragma_storage_info('<table>') WHERE compression = 'Uncompressed'` before and
after and fail loudly if it did not fall. Without the verification there is no way, from outside, to
tell a checkpoint from a no-op. The comparison harness's `CHECKPOINT=1` does exactly this and fails
the cell rather than reporting an uncompressed measurement as a checkpointed one.

#### 2. DuckDB checkpoints DURING ingest on its own, and it is a loss - suppress it

`checkpoint_threshold` defaults to **16 MiB**, and at some payload shapes a COMMIT inside `append`
triggers an automatic checkpoint. It charges compression time to ingest AND leaves the table
half-compressed, so the final manual checkpoint pays to finish a mixed table.

**This is what the 500k "anomaly" was.** The first curve had 500k costing 495 ms - four times the cost
of checkpointing 2M rows - and reproduced it in a fresh process, so it was not an ordering effect.
The matrix (`tools/probe/checkpoint-fragmentation.mjs`, same row count ingested as 1/4/20/40 payloads,
fresh database each time):

| auto-checkpoint | rows | payloads | pre-compressed segments | ingest | final CHECKPOINT | TOTAL |
|---|---|---|---|---|---|---|
| default | 500,000 | 20 | **241** | 1,033 ms | **500 ms** | 1,533 ms |
| **auto-off** | 500,000 | 20 | 0 | 720 ms | **148 ms** | **868 ms** |
| default | 500,000 | 40 | **471** | 1,893 ms | 66 ms | 1,959 ms |
| **auto-off** | 500,000 | 40 | 0 | 759 ms | 144 ms | **903 ms** |
| default | 2,000,000 | 20 | 0 | 2,798 ms | 298 ms | 3,096 ms |
| auto-off | 2,000,000 | 20 | 0 | 2,789 ms | 339 ms | 3,128 ms |

- With `SET checkpoint_threshold = '1TB'` during ingest, 500k/20 costs **148 ms** - on the line with
  1M's 156 ms. The anomaly is gone, and it was never about the row count.
- **Total time falls 1.8x and 2.2x** at 500k. At 2M no automatic checkpoint fires in this shape, so
  suppressing costs nothing. There is no shape measured where allowing it wins.
- Which shapes trigger it is not a clean function of payload size (5k, 50k and 100k-row payloads did
  not; 12.5k and 25k did), so **do not reason about when it fires - suppress it and checkpoint once.**

#### 3. What a checkpoint costs, per size

30-column corpus, 20 payloads, auto-checkpointing suppressed, armed and verified, two repeats that
agree, answer re-checked after every checkpoint (`tools/bench/checkpoint-cost.mjs`):

| rows | ingest | CHECKPOINT | ms/1M rows | immediate repeat | re-ckpt after +5% rows | 3 of 30 columns | DuckDB memory |
|---|---|---|---|---|---|---|---|
| 100k | 149 ms | **90 ms** | ~900 | 0 ms | 5 ms | 6 ms | 64 -> 14 MB (4.7x) |
| 500k | 684 ms | **148 ms** | 297 | 0 ms | 50 ms | 7 ms | 316 -> 62 MB (5.1x) |
| 1M | 1,341 ms | **156 ms** | 156 | 0 ms | 101 ms | 8 ms | 610 -> 121 MB (5.0x) |
| 2M | 2,731 ms | **324 ms** | 161 | 0 ms | 113 ms | 15 ms | 1,204 -> 240 MB (5.0x) |
| 5M | 1,586 ms | **1,042-1,285 ms** | 208-257 | 0 ms | 402 ms | 32 ms | 3,152 -> 588 MB (5.4x) |
| 10M | 1,870 ms | **1,512-1,593 ms** | 151-159 | 0 ms | 155 ms | 70 ms | 6,139 -> 1,188 MB (5.2x) |

- **~80 ms fixed plus ~150-250 ms per 1M rows** at 30 columns. Sub-1M is dominated by the fixed part.
- **Memory falls 4.7-5.4x at every size.** For a 64 GB worker holding a large result that is the
  difference between spilling and not, independent of any query speedup.
- **Arming is free** (0 ms) and **an immediate repeat is free** (0 ms, nothing dirty), so a defensive
  extra call costs nothing. What is NOT free is checkpointing repeatedly during ingest: a re-checkpoint
  after only 5% more rows costs 10-40% of a full one, so the cost is per-checkpoint, not per-new-row.
- **Cost tracks BYTES, not rows:** the same rows over 3 of the 30 columns is 5-73 ms against
  90-1,593 ms. A narrow projection is nearly free to checkpoint.

#### An ingest finding that fell out of the same matrix, and is bigger than the checkpoint

**Payload shape dominates ingest: 2M rows takes 164 ms as ONE payload and 2,798 ms as twenty - 17x.**
Consistent with DuckDB parallelising per 122,880-row row group (a 500k-row payload is 4 row groups and
can use 4 threads; a 100k-row payload is one group on one thread), and with the earlier finding that
batching paths into one `append` is ~4x a sequential loop. If the worker can hand several landed
payload files to a single `append({ parquet: [...] })`, that is worth more than the checkpoint is.
Not yet measured at the worker's real fetch cadence.

### THE COST OF A UDF IS LINEAR — THERE IS NO THRESHOLD (2026-08-20, CORRECTED)

**An earlier version of this section reported a parallelism cliff between two and three UDFs. That
was an artefact of the benchmark and is wrong.** `transform-mix.mjs` applied five DIFFERENT
functions to five DIFFERENT columns and forced them to UDF in a fixed order. The columns'
cardinalities were 100,000 / 2,000,000 / 5 / 4 / 2,000,000, so every step added a wildly different
amount of work. The compressed run's increments - **+45, +754, +13, -17, +852 ms** - track column
cardinality almost exactly and the UDF count not at all. The "cliff" was the 2M-distinct column
arriving second.

Re-run with the variable isolated - the SAME function on the SAME column N times, each with a
different argument so each is a separate registration doing identical work, 2M rows:

| udfs | uncompressed ms | cores | delta | checkpointed ms | delta |
|---|---|---|---|---|---|
| 0 | 31 | **9.2** | | 33 | |
| 1 | 385 | **1.5** | +354 | 369 | +335 |
| 2 | 739 | 1.4 | +354 | 706 | +337 |
| 3 | 1,079 | 1.2 | +340 | 1,035 | +330 |
| 4 | 1,526 | 1.2 | +446 | 1,372 | +337 |
| 5 | 1,741 | 1.2 | +216 | 1,736 | +364 |
| 6 | 2,075 | 1.1 | +333 | 2,078 | +342 |

1. **The cost is LINEAR in the number of UDFs.** ~342 ms each, no step anywhere. There is no
   threshold at two, three or any other count.
2. **That ~342 ms per UDF over 2M rows is 171 ns per value** - which independently reproduces the
   ~178 ns/value marshalling cost measured in the CONCURRENCY section by a completely different
   method. Good corroboration of both.
3. **Parallelism collapses at the FIRST UDF, not the third**: 9.2 cores to 1.5. The earlier
   "6.6 cores with one UDF" reading was true of that query but not of UDFs in general - its
   all-SQL baseline was 579 ms of native work on 2M-distinct columns, so one cheap UDF was a small
   fraction of the total and the native parts still parallelised. `cores` measures the WHOLE query:
   a UDF serialises its own work, and whether the query still looks parallel depends on how much
   parallel work sits beside it.
4. **Compression barely mattered here** (2,075 vs 2,078 ms) because `name` has 100k distinct values
   over 2M rows - scattered across 122,880-row groups, nearly every row in a group is distinct, so
   there is no dictionary win to have. The per-distinct-value effect needs a genuinely repetitive
   column; see THE CHECKPOINT PAYBACK.

**The conclusion for the promotion work survives, for a better reason.** Each promotion removes a
fixed ~171 ns per value from the query, independently of how many others are promoted. There is no
cliff to get over and no need to finish before seeing benefit - but equally, no bonus for
finishing: the last UDF in a projection is just as expensive as the first.

#### 3. Ingest levers — and the append question, answered against DataFrame

Every lever crossed against in-memory and file-backed. **Refuted: connection pooling (no gain -

**The honest answer to "does append cost sink us for long jobs":** append is 15-45 ms per 50k
payload against `DataFrame.appendAll`'s 0.2 ms, so **17-52 appends consume one aggregation's worth of
advantage**. For an append-dominated job that never pays back. Append cost is FLAT as the table grows
(measured to 8M), so it does not degrade - but it does not amortise either.

#### 4. Parquet as the table — the direction this points to

Querying the payloads directly makes ingest free, and it holds up far better than expected:

- the tax is **~32-45 microseconds per ROW GROUP per query** — **CORRECTED 2026-08-24 from "per
  file"**, and the old table's own data had already falsified the per-file reading (see below);
- the knee is at **~100k rows per file**, which is DuckDB's default row group (122,880) - at 100M
  rows, 100 files and 1,000 files cost the SAME **because they hold the same number of row groups**,
  not because a per-file tax stopped mattering. **Size payloads to at least one row group, and never
  lower `ROW_GROUP_SIZE` on the producer;**
- on real queries a 100-file view MATCHES a materialised table (selective filter 143 ms vs 141 ms);
- materialising 100M rows costs 31.9 s and 11.3 GB, payback **158 queries**. In memory at that size
  it is actively counterproductive;
- **compaction beats materialising**: 5,000 -> 100 files costs 10 s at 25M and gets queries to 12 ms,
  where a table costs 13.6 s to reach 0.9 ms;
- **S3 works, if configured.** `enable_http_metadata_cache`, `parquet_metadata_cache` and
  `httpfs_connection_caching` are ALL OFF by default; turning them on takes a two-predicate search
  from transferring 40.7 MB to **5 KB**, cuts S3 from 4-6x local disk to ~1.5x, and fixes an outright
  connection failure at 1,000+ files. This is the highest-value configuration decision for remote
  payloads.

### CHECKPOINT CADENCE ON A FILE-BACKED TABLE (2026-08-20) — checkpoint OFTEN, it is nearly free

> **READ THIS WITH THE 2026-08-21 AND 2026-08-24 RESULTS, WHICH NARROW IT SHARPLY.** This section's
> "nearly free" holds at a ~1M cadence and nowhere below it: at 250-500k it doubles-to-triples ingest
> (§THE 2026-08-21 SESSION), and suppressing checkpointing altogether is a further 1.45x on append
> (2026-08-24). The reconciled picture: **checkpoint cost is per-CHECKPOINT, so cadence is the whole
> question** - never during ingest is fastest, ~1M is nearly free, below ~500k is ruinous. The reason
> to checkpoint at all during a long ingest is **footprint, not speed**: suppressing it costs 3.6x disk
> and 1.44x RSS at 5M. Pick the coarsest cadence that keeps peak footprint inside the container.

**This measures a different thing from §THE CHECKPOINT PAYBACK, and gets a different answer.** That
section measured an IN-MEMORY table, where a checkpoint cut memory 5.4x. This one streams 10M rows
into a **file-backed** database the way the worker really does - 100k Parquet payloads, 10 appends
in flight - and sweeps how often `CHECKPOINT` is issued
(`tools/bench/scale-ingest.mjs`, 30-column corpus, darwin/14-core/36 GB).

| cadence | checkpoints | checkpoint cost | INGEST | peak RSS | final disk |
|---|---|---|---|---|---|
| never (control) | 0 | — | 84.7 s | 5,927 MB | 1,159 MB |
| **every 1M** | 10 | 6.5 s | 82.4 s | **6,053 MB** | **1,188 MB** |
| every 2.5M | 3 | 2.2 s | 85.9 s | 6,198 MB | 1,189 MB |
| every 5M | 2 | 1.6 s | 85.8 s | 6,364 MB | 1,337 MB |
| every 10M (one, at the end) | 1 | 0.8 s | 82.4 s | 7,383 MB | 1,486 MB |

Four things fall out, and the first is the one that overturns the worry:

1. **Checkpointing does NOT slow ingest.** 82.4-85.9 s across every cadence - the spread is noise,
   and the *most* frequent cadence produced the joint-fastest run. The fear that "if it does it too
   much it slows down" does not materialise on a file-backed table.
2. **A checkpoint costs a roughly FLAT ~700-830 ms regardless of how much accumulated since the
   last one.** 1M or 5M of new rows, the bill is the same; only the very first one is cheap
   (156 ms). So the cost model is per-CHECKPOINT, not per-row - which means rare checkpoints do not
   save anything, they just defer.
3. **Rarer checkpoints cost MEMORY**: 6.05 GB at every-1M rising to 7.38 GB when deferred to the
   end, ~18% - so the cadence is the RAM lever, just a gentler one than in memory.
4. **Rarer checkpoints also cost DISK**: 1,188 MB vs 1,486 MB, 20% larger, because deferred pages
   stay uncompressed.

**Guidance: checkpoint every ~1M rows on a file-backed table.** It is the cheapest point on every
axis measured, and 6.5 s of checkpointing inside a 97 s run is 7% for a 1.3 GB memory saving and a
20% smaller file.

Note the control was never fully uncompressed: even with no explicit checkpoint only 460 of 11,766
segments were uncompressed, because **DuckDB auto-checkpoints during ingest anyway** - the trap
recorded in `append-ingest.mjs`. An "uncheckpointed" file-backed run is not what it sounds like.

### THE CHECKPOINT PAYBACK, PER OPERATION (2026-08-19) — it is not a win everywhere

Two full comparison sweeps, DuckFrame only, identical corpus, `CHECKPOINT=0` and `CHECKPOINT=1` into
separate result files, differenced by `tools/bench/checkpoint-payback.mjs`. 69 cases measured both
ways at 100k/1M/5M, and **row counts agree on every one** - nothing "won" by doing less.

| case | 100k | 1M | 5M |
|---|---|---|---|
| transform (array column) | 1.5x | 4.6x | **10.4x faster** |
| validation (isIP) | 1.5x | **7.8x** | 2.2x |
| transform (toUpperCase) | 1.2x | 3.1x | **4.8x faster** |
| 5 transforms + filter | 1.0x | 2.4x | **4.0x faster** |
| group by 1 key + sum | 2.3x | 1.6x | 2.9x |
| filter (1 of 5 matches) | 2.1x | 1.6x | 2.3x |
| group by 2 keys + 3 aggs | 1.8x | 1.2x | 1.3x |
| join / ldjson / export / append / ingest | ~1.0x | ~1.0x | ~1.0x |
| **sort (2 keys)** | 1.0x slower | 1.3x slower | **1.4x slower** |
| **sort + limit (top 1,000)** | 1.2x slower | **2.3x slower** | 1.6x slower |
| **page (limit 1,000)** | 1.2x slower | **2.8x slower** | 1.3x slower |
| **dedup (all columns)** | 1.0x | **1.8x slower** | 1.1x slower |
| **read from the wire** | 1.0x slower | 1.0x slower | **1.6x slower** |

**So the checkpoint is a per-PLAN decision, not a default.**

1. **UDF-bearing transforms are where it pays**, and more as data grows: 2.95 s -> 283 ms on the
   array-column transform at 5M against a 976 ms checkpoint, so one pass repays it. `toUpperCase`
   saves 1.11 s against a 1.07 s checkpoint - break-even on the first pass, profit on the second.
2. **Sorts, top-N, paging and dedup get WORSE, up to 2.8x.** Nothing there benefits from a dictionary,
   so compression only adds decompression to a scan. A plan that sorts and pages after transforming
   gives part of the win back.
3. **SQL emission and the checkpoint are substitutes, and emission is the better buy.** Those 3-10x
   transform wins exist *because* the transform is a JS UDF called once per row; once the function
   runs as native SQL the per-distinct-value effect has nothing to bite on. Emission costs no
   1-second tax and does not slow sorts down. Prioritise it.

Caveat on precision: `RUNS` is 2 at 1M and **1 at 5M**, so anything within about 1.2x is inside
single-sample noise - which covers most of the "slower" rows for join, export, append and ingest,
whose setup does not even take a checkpoint (their tables are built inside the measurement). The
large numbers, in both directions, are well outside it.

### THE 2026-08-18 MEASUREMENTS — read this before optimising anything

Five sections were merged here. Two of them had to be corrected after Jared pushed back, and those
corrections are the most useful part: **verify the measurement before believing the finding.**

#### The rule that invalidates thread measurements on small data

DuckDB parallelises per ROW GROUP of 122,880 rows: *"for a query to run on k threads, it needs to scan
at least k * 122,880 rows"* (`guides/performance/how_to_tune_workloads`). A 500k table has **5 row
groups**, so it cannot exceed ~5 threads whatever `threads` says. My first pass concluded "SQL
saturates at ~4 cores" from exactly that artifact; **withdrawn**. `SET threads` itself was fine -
verified with `current_setting('threads')`. **Never measure thread scaling below ~2M rows.**

#### A JS UDF is single-threaded; SQL is not

5M rows x 30 columns (41 row groups), `cores` = `process.cpuUsage()/wall`, so cores actually used
(`tools/bench/udf-threads.mjs`):

| shape | t=1 | t=4 | t=14 | cores@14 |
|---|---|---|---|---|
| passthrough (30-col write) | 2,484 ms | 559 ms | 606 ms | 6.0 |
| sql x1 (`upper`) | 2,464 ms | 588 ms | **251 ms** | **10.7** |
| sql x5 | 3,644 ms | 962 ms | **403 ms** | **9.2** |
| udf x1 | 3,650 ms | 1,080 ms | 1,055 ms | 4.2 |
| **udf x5** | 10,875 ms | 7,372 ms | **7,357 ms** | **1.8** |
| **udf x1, aggregated (no write)** | 994 ms | 959 ms | **997 ms** | **1.0** |
| sql x1, aggregated (no write) | 55 ms | 15 ms | **8 ms** | 8.8 |

The aggregated pair is the proof - no table write to hide behind. **18x** on the five-function
pipeline, **125x** isolated. **These two ratios are real FOR THIS SYNTHETIC and do not generalise:**
the same five-function shape on the real corpus is **2.98x at 1M** (§2 What the promotions bought).
Quote them only as "what the UDF boundary costs when a query is nothing but UDFs". The plan around a UDF still parallelises (udf x1 uses 4.2 cores), so
DuckDB is not refusing; the callback is the serial section. It is Amdahl, not a flat tax.

**The cost is marshalling, not our code** (2M rows, aggregated, `tmp/udf-cost.mjs`): an **empty**
callback is **178 ns/value**; with our converters and the real function 198 ns; three string ops
208 ns; native SQL **1-2 ns**. So converter/function micro-optimisation cannot matter - it is ~10%.
Flat across 500k/2M/5M, so per-value, not per-chunk.

**Mechanism, from primary sources** (`research/client-udf-parallelism.md`): node-neo hands each call to
a `TypedThreadSafeFunction` created with ONE thread and **blocks the calling DuckDB worker** until JS
returns; its README says callbacks are "serialized even when DuckDB scans in parallel".
`duckdb/duckdb#14817` (Python UDFs not parallel) is closed as not planned. But the C API expects
concurrency - `duckdb_scalar_function_set_init` is "called once for each worker thread" - and **Rust and
Java both genuinely parallelise**. So this is a Node-binding property, not a DuckDB one.

#### CHECKPOINT the master table — the cheapest win available

An in-memory table is `Uncompressed`; DuckDB only compresses at checkpoint. Uncompressed means flat
vectors, so a UDF runs once per ROW. After a checkpoint, low-cardinality columns are `DICT_FSST` and the
UDF runs once per dictionary entry per row group. **Build in memory, then ONE `CHECKPOINT` when ingest
is quiesced.**

Strategy, 5M rows / 20 payloads, real ingest path, all five verified to return identical answers
(`tools/bench/checkpoint-strategy.mjs`); "ready" = create -> queryable, "transform" = 30-col projection
with one UDF column:

| strategy | ready | transform | udf calls | DuckDB memory |
|---|---|---|---|---|
| in-memory, no checkpoint *(today)* | 1,647 ms | 1,025 ms | 5,000,000 | **3,152 MB** |
| **in-memory, ONE checkpoint at end** | **2,618 ms** | **261 ms** | **3,130** | **589 MB** |
| in-memory, checkpoint every 5 payloads | 3,328 ms | 260 ms | 3,125 | 608 MB |
| file-backed, default (auto-checkpoints) | 5,559 ms | 1,124 ms | 3,180 | 580 MB |
| file-backed, auto off + one at end | 6,473 ms | 1,590 ms | 3,130 | 579 MB |

~200 ms per 1M rows, once. Buys **5.4x less memory** and **3.9x on the transform**. Checkpointing more
often is pure loss. **A file-backed master is worse on every axis** - compressed-in-RAM beats
compressed-on-disk; do not move the master table to a file.

Per-operation, 2M rows, before -> after (`tools/bench/checkpoint-effect.mjs`): udf low-cardinality
**375 -> 4 ms (104x**, 2,000,000 -> 13,540 calls); sql `upper` 3 -> 1 ms; filter 2.6x; group-by 3.5x;
distinct 1.2x; sort+limit 1.2x; **join, row->json and a UDF over a UNIQUE column: no change**. So it is
**not** the docs' general 8x - it is memory, plus a large win bounded by cardinality.

**Two traps, measured:** a `CHECKPOINT` during concurrent appends returns in 111 ms and does **nothing**
(rows in open transactions cannot be compressed) - no error, still `Uncompressed`; and payloads appended
**after** a checkpoint arrive uncompressed (13,540 -> 213,540 calls), healed by a re-checkpoint.

**Consequence:** `docs/PERFORMANCE.md` and every UDF number in this file were measured uncompressed.
They are the worst case for repetitive columns; they stand for unique ones.

**And this reverses the ingest verdict for TRANSFORMS only:** §INGEST COST rejected the raw-buffer path
because coercion dominated and fixed-width types were already at parity. Transforms have neither
property - 178 of 198 ns IS marshalling - so `vector_get_data`/`copy_data_to_vector` are worth a probe
there. Unmeasured.

#### The parity objection to SQL does not hold as stated

`duckdb-parity.md`'s divergences, and the "11 divergences / 26 of 40 casts" line quoted all over this
file, were measured against DuckDB's **default cast** (`TRY_CAST(v AS TINYINT)` etc). That proves
DuckDB's casts differ from our coercion. It does **not** prove SQL cannot express our semantics.
Re-tested with deliberate expressions (`tools/probe/sql-semantics.mjs`): **13 of 13 previously-divergent
inputs match data-mate exactly.**

| input | data-mate | naive `TRY_CAST` | deliberate SQL |
|---|---|---|---|
| `12.7`, `2.5`, `-2.5` -> Byte | 12, 2, -2 | 13, 3, -3 | `TRY_CAST(trunc(v::DOUBLE) AS TINYINT)` |
| `0x10`, `0b11`, `1e3` | 0, 0, 1 | 16, 3, 1000 | `regexp_extract(v,'^[+-]?[0-9]+')` then cast |
| `'y'`, `''` -> Boolean | THROW, false | true, null | `CASE ... ELSE error('...') END` |
| `1710028800000`, `Mar 10 2024` -> Date | parsed | null | `epoch_ms(v::BIGINT)`, `try_strptime(v, [formats])` |
| `01.02.03.04`, `1.2.3.4/24` -> IP | THROW | accepted | regex guard + `error()` |

`error()` reproduces a THROW and `try_strptime` takes a LIST of formats - those two unlocked it. Cost of
SQL emission is therefore "one deliberate expression per function plus a golden test", and
`tools/parity/` already drives both paths. **Also, two surfaces were being conflated:** those
divergences are INGEST COERCION (string -> typed value); the 205 functions run AFTER coercion on typed
values, so transform parity is a smaller problem, not the same one. The genuine residue of risk is
JS-flavoured semantics: number formatting at the extremes, JS regex vs RE2, date format tokens.

#### Coverage for the 205, and three traps

Detail in `research/sql-function-coverage.md`. **Native and in-engine:** string case/trim/pad/split/
similarity; RE2 regex; `md5`/`sha1`/`sha256` (no `sha512`); `url_encode`/`url_decode`, base64, hex;
`error()`; date parse/format/truncate/parts/diff; icu timezone shifting; `inet` containment (`<<=`,
`>>=`), `host`, `network`, `netmask`; JSON extraction and `json_valid`; the whole `list_*` family.

**NO native equivalent** - the only candidates for a native extension: MAC/EUI (nothing at all),
IPv4-vs-IPv6 discrimination, masklen/abbrev/inet_merge, IP<->integer, geohash, index-accelerated
radius/KNN, metric-radius `ST_DWithin` on GEOMETRY (planar only; spheroid variants are POINT_2D-only),
JSON Schema validation, jq-style paths, fuzzy date parsing, non-English month/day names, business-day
arithmetic, and any regex needing **lookahead / lookbehind / in-pattern backreferences** (RE2 rejects
all three, measured). No native `isEmail`, `isMACAddress`, `isPostalCode` - regex, or stay JS.

1. **`ST_Distance_Sphere` / `_Spheroid` take (lat, lon)** - the reverse of `ST_Point(x=lon, y=lat)`.
   NYC-London measured **5,570 km swapped vs 8,247 km correct**. Short-radius tests hide it. Pin the
   argument order with a long-distance assertion.
2. **`strptime`/`strftime` formats must be CONSTANT** - not from a column. Fine for us: a QPL format is
   a directive argument, i.e. a plan constant. Part names, zone names and JSON paths may be per-row.
3. **`@duckdb/node-api` renders TIMESTAMPTZ in the INSTANCE-CREATION zone and ignores `SET TimeZone`**;
   DuckDB's TIMESTAMPTZ rendering is session-dependent generally. **Always format server-side** -
   `strftime(ts AT TIME ZONE 'UTC', ...)` or `epoch_ms(ts)`. The export projection already does; do not
   regress it.

Minor: `duckdb_timezones()` does not exist (it is `pg_timezone_names()`, 638 rows); `spatial` does NOT
autoload, though `icu` and `inet` do.

### DO NOT

- **Do not reintroduce JSON.** No `read_json`, no ndjson staging, no JSON.stringify of
  records. There is no JSON in the lifecycle; the ES client returns parsed objects and the
  wire carries Parquet. A `read_json`-based SQL coercion layer was built, measured as a net
  loss, then extended for ten more increments on sunk cost, then deleted (~2,000 lines).
- **Do not reimplement field semantics in SQL.** Use `coerceToType` and the other
  `core-utils` / `ip-utils` / `geo-utils` primitives, in a UDF if needed. Reimplementing is
  what produced 11 divergences plus three null-handling bugs that `callIfNotNil` makes
  impossible.
- **Do not gzip the transport.** Parquet zstd is smaller and ~50x cheaper to produce.
- **Do not mutate a frame's table in place.** Relations read it by name, so an
  UPDATE/DELETE/INSERT would silently change every derived frame.
- **Do not add API on spec.** `toArray()` was added because `DataFrame` has one; spaces
  never calls it, and it carried a bug tracked as debt for three increments. `getColumn` is
  the most-used frame method in spaces and is deliberately absent - all 7 uses extract a
  resident JS vector, which cannot port.

> **READ `ingest-findings.md`'s STOP block FIRST.** Ingest is `coerceToType` in JS plus a
> typed DuckDB appender — **no JSON, no SQL coercion layer, no UDFs**. A `read_json`-based

- **Do not let DuckDB make the HTTP call.** Technically works, but Jared rejected it: httpfs is a
  dumb GET, while the real reader has auth, POST bodies, slicing, retries and backpressure.
- **Joins**, 1M x 20M at 1M distinct keys: flat 555 ms, per-parent `fetch:10` 1,322 ms, `@first`
  870 ms, LEFT JOIN 495 ms. These are a **pure DuckDB probe over synthetic tables**, not
  measurements of the engine. ⚠ **Produced at the INVALID 6GB/2-thread envelope** — re-run
  `tools/bench/join-shapes.mjs`, whose defaults are now the worker's.

### Spaces architecture, as verified

- **One Docker image**, three roles by command: `api-server`, `task-runner-origin`,
  `task-runner-child`.
- **Synchronous queries run entirely in the api-server.** The forked `spaces_qpl_worker` (64 GB)
  handles `long_running=true`, and the intent is to make that the default.
- **The reader never talks to Elasticsearch.** It POSTs to the spaces search API.
- **Non-long-running queries have no row limit** — a 2-minute wall clock.
- **Joins fan out today**: one child search per parent row, mitigated by a 10,000-entry LRU that
  high cardinality defeats. That is the motivation for a real SQL join.
- **The 205 functions ARE the QPL language** (`v3/type-defs/directives.ts:189-224` generates a
  directive per function and alias). Function drift is a public API break.

## Appendix B. Environment traps — still current

- **A PostToolUse formatter fights the repo's eslint.** It rewrites whole files to
  2-space/double-quote; the repo is 4-space/single-quote, and `eslint --fix` does NOT fully undo
  it. The hook matches `Edit` only, so **use `Write` or a script for `.ts`/`.js`**, then check
  `git diff --stat` — a large diff for a small change means formatting churn. Never route around
  eslint itself.
- **Runner import errors usually mean a stale `dist`.** `js-yaml does not provide an export named
  'default'` was a two-month-old local build, not a broken runner. `pnpm build` at the repo root.
  **Use `ts-scripts`, never jest directly** — and the flag is `-- --testPathPatterns <p>`.
- **Jest ignores mid-process `TZ` changes** — the VM context caches it at startup. That is why
  D5's timezone half has no test; reproduce it outside jest.
- **`timeout` does not exist on macOS.** It exits 127 ("command not found"), which reads as a
  failing script. Cost a full round of false "broken" verdicts.
- **`node -e` leaves `process.argv[1]` undefined**, which breaks `isExecutedFile` and made 18
  healthy bench files look broken. Use a real script file.
- **Do not benchmark through jest** — ~4x pessimistic (swc, module registry, coverage).
