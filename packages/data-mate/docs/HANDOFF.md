**THE INPUT IS A `QueryAccess` STATEMENT (2026-09-21).** Spaces drives every query and execution plan

already applied — is 80%+ of what a frame is handed. `frame.query(sql)` runs one and returns a frame;

a relation there:** a generated statement may name its source more than once (a self-join, a correlated
subquery), and a relation is textual so each mention re-executes the whole subquery. Pinned end to end
by `test/duck-frame/query-access-spec.ts`.

**`@terascope/sql-builder` is a NEW package (2026-09-21).** The dialects, quoting, clause building and
statement assembly moved out of `xlucene-translator` into it, and `data-mate` consumes it, so the
translator and the frame render SQL with the same code without either package depending on the other.
That is what fixed the null-placement divergence; see §DESIGN POINTS.

**188 of the 205 field functions emit native SQL** instead of a JS UDF — 51 date, 50 numeric, 46
string, 21 IP, 13 geo, 3 boolean, 2 object, 2 json — gated both ways over a typed battery. **Read
`sql-emission.md` before adding another.**

| | |
|---|---|

| **the worker** | **persist each payload AS RECEIVED. No append, no consolidation, no table** |

**BYTES PER MILLION DEPENDS ON THE CORPUS — always say which one.** 28.0 MB/M is the periodic
synthetic (`bench/comparison`, cross-checked by the wire's 22.8 MB/M), ~106 MB/M the 2026-08-27 query
fixtures, **33.9 MiB/M real NOAA** (691,122,937 records in 22.87 GiB, `FIXTURE=noaa`). A generator
built on `i % N` compresses ~2x better than real data; see §0.8 and `s3-perf/fixtures/README.md`.

**The cost model: the ROW GROUP is the unit of query cost** — 26-44 µs per row group, file count
absent from the law. The decisive pair: 100 files/100 groups and 20 files/100 groups both answer
`count(*)` in **4.1 ms**. DuckDB's default row group is **122,880 rows** and `qpl-search-api` caps a
slice at **100k**, so **no payload can ever fill one**; never lower `ROW_GROUP_SIZE` on the producer.

**THE ONE MEMORY CLIFF, precisely bounded.** A **wide top-N** (`SELECT * … ORDER BY … LIMIT`) over
Parquet needs between 512 MiB and 1 GiB and **fails rather than degrading**; 14 of 15 query shapes
are fine down to 128 MiB. The law is **threads × row-group × columns projected, INDEPENDENT of
dataset size** (identical at 10M and 100M) — **fix: never emit `SELECT *`**, or cap threads (4
suffices at 256 MiB), or budget ~1 GiB per concurrent wide query.

**`duckdb_memory()` IS NOT RESIDENT MEMORY** — it is elastic buffer-manager residency and equals the
database file size whenever the limit is generous. **Plan with peak process RSS** (§0.11).

**Also settled:** a `VIEW` over `read_parquet` is identical to inlining it, and a glob to a path
array; Arrow IPC is out (2.1x at 100k rising to 8.1x at 1M, 3.9x the disk), CSV/NDJSON ~17x.

**Still not built:** `deepSelect`/`_skip_if_empty`, stacked `expand_values` (`UNION ALL`), the
date/timezone offset column (unblocked — `icu` is loaded and the idiom is verified), and the
remaining 17 functions. **`spatial` must be packaged** before the 13 geo emissions run anywhere but
a dev box — they have **no UDF fallback** (DF7), so those queries fail outright without it.

**Traps that cause silent wrong answers:** `ST_Distance_Sphere` takes (lat, lon); a CHECKPOINT during
concurrent appends does nothing; a macro can shadow a built-in; TIMESTAMPTZ renders in the driver's
zone; RE2 has no lookaround; **`memory_limit` does not bound process RSS** (Parquet's RSS was ~5 GB
under a 1 GiB limit).

**Defects in `known-defects.md`** (DF1, DF2, DF4-DF13). Three deserve tickets: **DF8** (geo-utils
calls a shape not-contained when it merely TOUCHES a hole), **DF9** (`isBase64` rejects 99.3% of
valid base64), **DF6** (`addToDate` answers differently per server timezone).

## 0. THE CORRECTIONS THAT KEEP RECURRING — ITEMS 0 THROUGH 13, READ THEM ALL

Each was gotten wrong at least once, several three or four times, and every one cost real work.

**0. THE FLOW. Explained FIVE times. Get this right before touching anything.**

```
qpl-search-api   queries Elasticsearch -> RECORDS. The ONLY place records become a frame
                 (DuckFrame.fromRecords). Sends PARQUET back over the wire.
qpl-worker       WHERE THE TABLE LIVES. Its slicers/fetches query qpl-search-api, each
                 returning a Parquet payload; it ingests the MANY payloads into ONE table
                 representing the entire search query result.
```

**`fromRecords` is NEVER called in qpl-worker** — multi-slice accumulation is worker-side and **from
Parquet** (`create()` + `append({parquet})`), never from records. **If any doc contradicts this
diagram, this diagram is right.** Do not ask about it again.

**0b. DO NOT DESIGN AROUND A CA CERTIFICATE — check the settings list first.** DuckDB 1.5.5 has
`enable_curl_server_cert_verification` listed right next to `ca_cert_file`, so a private-CA endpoint
needs no PEM at all; believing otherwise cost most of a session and misdiagnosed a config bug as TLS.
**Before concluding an engine cannot do something, `SELECT * FROM duckdb_settings()` and grep it — a
default is not a limitation.**

**0c. A FRAME OWNS A SECOND DATABASE, AND `open()` DOES NOT CONFIGURE IT.** `lib/duck.mjs`'s `open()`
and a `DuckFrame` are two DuckDB instances sharing nothing; a script that hand-copied "the settings
that looked relevant" omitted `LOAD aws/parquet/json`, the autoload switches and the HTTP
timeout/retries, and read as broken when it was a config divergence. Fixed by making
`applyEndpointSettings(run, overrides)` the single definition — **anything that opens a second
database must call it.**

**1. This is a NEW ENGINE, not a port.** Corrected 3+ times: match observable behaviour and the 205
functions, because the old engine's internals (`QueryScope`, `JoinChanges`, `Builder.mset`,
`SearchLoader`'s LRU, `scope-utils.ts`'s per-row correlation) are one implementation chosen under
`DataFrame`'s constraints and are not a design input. Read `qpl-engine` to extract *what a query must
produce*; never ask "what does `X.ts` become", and read every "the old code does it this way, so…"
inference with suspicion.

**2. Know the tiers before measuring anything.** Explained 3 times: **api-server** fetches and
produces **Parquet+zstd**, the forked **qpl-worker (~64 GB)** runs the query including joins, and the
wire carries Parquet — never objects or JSON. Any join benchmark at 6 GB / 2 CPU measures the wrong
tier and is invalid.

**3. Never inherit a probe's parameters.** `tools/bench/join-shapes.mjs` used to default to `MEM=6GB
THREADS=2`, so reproducing a recorded finding reproduced its wrong premise. Define a benchmark from
the deployment envelope.

**4. Use the function configs. Do NOT invent a parallel vocabulary.** A `FunctionDefinitionConfig`
already defines name, aliases, `argument_schema`, `accepts`, `output_type`, the implementation and
`process_mode`, and spaces turns them into **GraphQL directives**, so they are the public surface.
`duckFrameAdapter` exists for exactly this; a hand-rolled spec type was built once and deleted.

**5. Explore a package's structure before adding to it.** The DuckDB type mapping was first dropped
in as a one-off `data-types/src/duckdb.ts`, when the package defines each FieldType as a class in
`src/types/v1/` and it belongs as a fourth method beside `toESMapping`/`toGraphQL`/`toXlucene`.
Likewise the DuckDB adapter belongs in `src/adapters/` next to the others.

**6. Put the design in a message BEFORE writing code.** Two substantial pieces were written and then
deleted because the shape was wrong.

**7. Verify how you MEASURE, not just what you measure.** Two false "the process hangs" findings came
from broken detection — `pgrep -f <script>` matches the enclosing bash process, and `kill -0 $pid`
succeeds for an unreaped zombie. **Use `wait $pid`**, and when two runs of the same config disagree,
fix the harness before theorising.

**8. A CONFOUNDED AXIS will hand you a confident law with the wrong variable in it.** Every Parquet
sweep varied file count at a fixed total, so "more files" and "more row groups" moved together in
every cell and the write-up named **files**; the real unit is the **row group**, and forcing 100 files
to hold 5,000 groups made them 16x slower with file count untouched.

- **The old table already contained its own refutation:** under a per-file law every cell in the
  `100 files` column must be equal, and 25M cost 12.0 ms against 4.0-4.2 ms because it held 3 groups
  per file. **When a column that should be flat is not, that is the finding, not noise.**
- **Name the unit, then try to break the coupling** — one run holding the suspected unit constant
  while the other swept 50x. If two candidate causes cannot be separated by the benchmark's own axes,
  it cannot support a causal claim yet.
- **Census, do not infer:** the bench counts row groups with `parquet_file_metadata` before measuring,
  because DuckDB rounded a requested 5,000 up to ~6,144 in a probe.

**9. Do not benchmark two things at once.** The `ROW_GROUP_SIZE` runs and the ingest pair were kept
strictly serial, because two DuckDB benches sharing 14 cores produce four wrong numbers and none
obviously so.

**10. A RATIO IS NOT A RECOMMENDATION. Compute BREAK-EVEN and lead with it.** In this system the cost
is paid ONCE PER JOB and the benefit is PER QUERY, so the deciding number is **Q, the query count** —
and §0.0's flow says Q is small. Jared caught the same error three times in one session:

| # | what was recommended | the ratio quoted | what was ignored |
|---|---|---|---|
| 1 | materialise a table | queries 2-20x faster | the job is append-dominated |
| 2 | stitch payloads to ≥123k rows | 11x on selective queries | the rewrite cost; ~2M is 3x cheaper |
| 3 | consolidate at the realistic slice mix | "~2x, only 4 s" | **break-even was 67 queries** |

- **`extra_one_time_cost / saved_per_query = Q_required`** — print it and compare it to real Q; if Q
  is unknown, the recommendation is **undetermined**, so say so instead of picking.
- **Seconds against milliseconds must trigger this automatically**, and **show the columns break-even
  derives from** (saved/query, extra cost). A battery total hides the distribution: 82% of one 60 ms
  "saving" was `top 100 rows`, and for aggregation-shaped work it was 30.5 ms and break-even doubled.

**11. A METRIC THAT TRACKS A FILE SIZE IS NOT MEASURING MEMORY.** `sum(memory_usage_bytes) FROM
duckdb_memory()` was published as "a Parquet view holds 65x less memory than a table", but the native
figure equalled the database FILE SIZE to four decimal places at every scale from 100k to 100M — it
is elastic buffer-manager residency, and by peak RSS the gap is **3.2x, not 65x**.

- **The decisive test for any "memory used" metric is to lower the limit**; if the number does not
  move, it is not resident memory. Same family as §0.8: a suspicious constant ratio IS the finding.

**12. "X IS FRAGILE" IS NOT AN ACTIONABLE FINDING — name the shape, the threshold, and the term it
scales with.** "A Parquet view OOMs under pressure where a table survives" was true and useless;
running every query individually across a limit sweep narrowed it to **one shape of fifteen** and gave
the law **threads × row-group × columns projected, independent of dataset size**.

- A blanket claim about a technology is almost always a claim about one query shape, and "needs
  ~1 GiB, fixed" is a capacity line item where "uses a lot of memory" is an anxiety. The mitigation
  fell straight out of the law: do not emit `SELECT *`.

**13. RE-CHECK WHETHER YOUR OWN BENCH IS MEASURING THE THING.** The consolidation bench timed each
target with `LIMIT n OFFSET k` per batch, which rescans from the start and is quadratic in batch
count, producing 12.0 s for 82 objects against 3.5 s for 20 and 14.6 s for 5. **Non-monotonic output
on a monotonic axis means the harness, not the world** — those numbers were excluded, and said so.

## 1. The DuckDB work (branch `dataframe-duckdb-refactor`)

### THE BOUNDARIES — who fetches, who joins, what data-mate owns

```
  Elasticsearch                 ES client returns PARSED JS OBJECTS
        v
  ===== qpl-search-api ==========================  the PRODUCER
  spaces' reader / fetch code    SPACES OWNS: auth, POST bodies, slicing, retries, backpressure
  DuckFrame.fromRecords          coerceToType + typed appender. VALIDATION HAPPENS ONCE, HERE.
  COPY ... (FORMAT PARQUET, COMPRESSION zstd)
  ===============================================
        |   *** THE WIRE CARRIES PARQUET + zstd. ***
        |   NOT objects, NOT JSON, NOT dfjson, NEVER gzipped.
        v
  ===== qpl-worker (~64 GB) =====================  the CONSUMER
  MANY payloads, one per fetch   its slicers/fetches each query qpl-search-api
  DuckFrame.create(config)       ONE table for the whole search result
  + append({parquet}) x N        read_parquet: 31 ms/1M, ZERO COERCION
  SQL: join / filter / project / agg    <== JOINS HAPPEN HERE
  ===============================================
```

Measured, 1M rows of the 30-column synthetic, every option ending at a queryable table on the worker:

| | producer | **worker** | wire |
|---|---|---|---|
| **parquet zstd** | 1,164 ms | **31 ms** | **22.8 MB** |
| ndjson | 803 ms | 248 ms | 194.0 MB |
| ndjson + gzip | 2,665 ms | 385 ms | 35.9 MB |
| dfjson *(today)* | 1,482 ms | 784 ms | 106.3 MB |

The **split matters more than the sum**: the worker is the scarce tier and is 8x cheaper with Parquet.
**The join strategy, decided:** load the whole dataset, let DuckDB overflow to disk, join it all at
once — not per-row fetches, not key-set batching, and do not design around a future semi-join pushdown.

### THE DEPLOYMENT ENVELOPE — measure at the right tier or do not measure

| tier | does | envelope |
|---|---|---|
| `api-server` | serves requests, **fetches**, produces Parquet | small; many concurrent queries per process |
| forked `spaces_qpl_worker` | **runs the query — joins execute HERE** | **~64 GB** |

- **A join benchmark MUST use the worker envelope**, and **`memory_limit` must be set BELOW the
  container's cap** — above it DuckDB never spills and the kernel kills the process, which produced
  the bogus "OOMs and does not spill" finding.
- **INVALID, DO NOT REUSE:** every number produced at `MEM=6GB THREADS=2`. With whole-table + file
  overflow, any operator that refuses to spill is a direct threat, not an abstract perf note.

### THE STORAGE DESIGN FOR SPACES — the decision record (2026-08-24)

Every option below was measured; tables in `PERFORMANCE.md`. This section exists because the same
ground was re-covered three times, each time reaching a different answer.

**The constraints, which are fixed and not design choices:**

- `qpl-search-api` is **stateless and distributed** — one request, ≤100k records, Parquet over the
  wire, consecutive slices possibly on different instances. **It cannot batch. Ever.**
- Real slices are a ragged 10k-100k mix, all below the 122,880-row group, so **no payload can fill one
  row group**; `qpl-worker` is the only stateful component, receives every payload's bytes, and is
  therefore the only place a batching decision can be made.
- The job is **append-dominated and aggregates rarely** (Q is SMALL), and local disk may not exist.

| option | verdict | the number that decided it |
|---|---|---|
| **append each payload into ONE table** | **REJECTED** | cost is per ROW (~1.88 µs/row + ~2.0 ms/statement). 258 s to absorb 100M against 6.2 s to land the bytes; break-even **272 queries** |
| **materialise a table at the end** | **conditional** | build is cheap (2.6 s / 20M, cheaper than rewriting Parquet) and queries 2-20x faster — but only pays if Q is large. Not the default |
| **query the payloads directly as Parquet** | **KEPT — the default** | ingest is free; a view is identical to inlining `read_parquet`, and a glob to a path array |
| **consolidate payloads into bigger objects** | **NOT by default** | 2-39x a byte copy. Break-even **67 queries** at the realistic mix, 132 aggregation-shaped. Only at consistently ~10k slices (break-even **5**) |
| **one single giant object** | **not reachable** | Parquet is immutable, so it means rewriting everything — and consolidated files already tie it on every real query |
| **Arrow IPC / CSV / NDJSON** | **REJECTED** | Arrow is 30x slower (no row-group statistics, every query full-scans), 16x the size, and loads slower than CSV |
| **native `.db` as the wire format** | **REJECTED** | 4x larger than Parquet+zstd, and zstd is *faster* to load at scale because I/O dominates decode |

```
qpl-search-api  ──Parquet+zstd over the wire──>  qpl-worker
                                                  │  persists each payload AS RECEIVED (a byte copy)
                                                  │  no consolidation, no table, no append
                                                  └─ queries them as a view / read_parquet glob
```

**The two switches, and what flips them:** consolidate (buffer to ~2M rows before the FIRST write,
never rewrite afterwards) when slices are consistently ~10k or Q is known to exceed ~50-130;
materialise a table when Q is large or point-lookups matter, since an ART index is 6-8x and Parquet
cannot have one at any price.

**S3 latency was the term that could have overturned this, and it did not.** `bench/report-s3.mjs`
with `lib/latency-proxy.mjs` at 100 ms RTT: the request-count model predicts 2.94 s for 87 objects
and measured **133 ms** — a ~22x over-prediction, because row-group statistics prune most objects and
the survivors are fetched concurrently. Latency raises the floor for every layout **equally**;
consolidation is worth ~1.2x under it, not the 8-30x the zero-RTT numbers implied. Still worth
confirming against a real bucket under concurrency.

| | |

**`select` and `join` take a verbatim `SELECT` list as well as a map**, because
`QueryAccess.restrictSQLParts` returns `select` as a pre-joined string and it cannot be turned back
into a map: the DuckDB dialect rebuilds a partly-readable STRUCT with `struct_pack`, so its projection
and its `columns` are deliberately not one-to-one, and reconstructing from `columns` silently drops the
field restriction. A verbatim list must be given `columns` — which `restrictSQLParts` returns beside it.

**THE API IS THREE GROUPS, and `filter`/`select` are NOT a search API** — a question Jared
raised 2026-09-22, because four methods looked like four ways to search:

1. **Compose a statement** — `filter` `select` `orderBy` `limit` `distinct` `join`. Six methods of
   ONE kind, each appending a clause. Their caller is the DIRECTIVE path: `duckFrameAdapter`
   returns one expression for one function on one column, so a transform chain is
   `select`→`select`→`select` and there is no finished statement to hand over.
2. **Be handed a statement** — `query` (instance) / `fromSQL` (static), the same pairing as
   `append({records})`/`fromRecords`. Their caller is `QueryAccess`. **Do not take a ready-made
   statement apart into `filter` + `select`** — that is how a field restriction gets dropped.
3. **Consume** — `rows` `size` `ndjson` `writeNDJSON` `writeParquet`.

**`rawRows` is in none of them: it is INSPECTION, and the justification is measured.** `rows()`
puts every value through `toPlainValue`, whose `bigIntToJSON` drops to the nearest double above
`MAX_SAFE_INTEGER` — on purpose, reproducing `DataFrame`'s defect so the two frames agree. On one
`Long`: stored `9007199254740993`, `rawRows` reports `9007199254740993`, **`rows()` reports
`9007199254740992`**. So `rows()` cannot be used to check `rows()` — an assertion about storage
made through the output path agrees with itself while the stored value is wrong, which is the
exact class of bug the storage checks exist to catch. Pinned by `duck-frame-spec.ts`
("should disagree with rows() above MAX_SAFE_INTEGER"); if that test ever goes green with both
paths equal, the divergence was fixed and `rawRows` has lost its main reason to exist. Secondary:
it needs no `DataTypeConfig`, so `DESCRIBE` need not invent one. Marked `@internal`; one caller in
`src/` (`schema-check.ts`).

**Large integers read back EXACTLY (2026-09-23).** `plain-values.ts` no longer calls `core-utils`'
`bigIntToJSON`, which subtracts 1 from every positive above the safe limit and silently rounds every
negative. `rows()` and `ndjson()` now agree by construction on the same `abs(value) > MAX_SAFE` rule.
`DataFrame` is knowingly left alone — see DEF-BIGINT in `known-defects.md` and
[#4555](https://github.com/terascope/teraslice/issues/4555).

**`info()` was REMOVED.** It bundled twelve fields, eleven of them already reachable (`table`,
`columns`, `from`, `isOrdered`, `isMaterialized`, `size()`); the twelfth was an `appends` counter kept
in two private fields solely so `info()` could report it, and what a caller actually has is
`append()`'s return value. `query(sql)` was the raw-rows escape hatch and is now `rawRows(sql)`, which
is what it does — the name was freed for the method that runs a statement.

Records are coerced by `coerceToType` — the SAME function the regular builder uses, so parity is by
construction — then appended as typed values through a DuckDB appender. Every query operation composes
relations, so a chain is ONE statement in a single pass and `materialize()` promotes one to a table.

### DESIGN POINTS THAT MUST NOT BE RE-LITIGATED

**`orderBy`/`limit` are ordinary relation-returning methods, not trailing state.** The optimiser
flattens a nested `ORDER BY` under an outer `LIMIT` into a byte-identical plan (`TOP_N` + a dynamic
scan filter): at 5M rows, nested 1 ms, flat 5 ms, unbounded sort 754 ms. Composition therefore comes
from SQL for free — `.orderBy(x).limit(10)` is the top 10, `.limit(10).orderBy(x)` sorts an arbitrary
10.

**Silent order LOSS is the real hazard, and it only appears at scale.** 5M rows / 14 threads, rows out
of a subquery ending in `ORDER BY x`: projection / `WHERE` / `LIMIT` / `OFFSET` = **0** out of order;
`JOIN` = 303, `GROUP BY` = 2,104, `DISTINCT` = 373 — and **both scrambling cases are perfectly ordered
at 20 rows**, so a small test proves nothing. Hence an `ordered` flag on `Source`, propagated through
order-preserving ops, with `join` / aggregating `select` / `distinct` **throwing** rather than
discarding it.

**Limit short-circuiting is real, but only with the limit IN THE SQL.** Unsorted `LIMIT` plans as
`STREAMING_LIMIT` and stops pulling (1 ms vs 68 ms to drain 5M); sorted plans as `TOP_N`, which cannot
exit early but uses a heap plus a dynamic filter that skips row groups. Breaking out of `rows()` stops
only the JS consumer.

**`distinct()` takes no arguments** — it is `SELECT DISTINCT *`, because `TableDedupNode` carries no
fields and the old engine calls `unique(frame.fields)`. Verified to compare LIST and STRUCT columns
and to treat NULLs as equal.

**What `qpl-engine` actually does with sort and paging** (checked in the spaces repo, not inferred):

| | where | what |
|---|---|---|
| `params.sort` + `start`/`size` | `v3/execute/search/fetch-from-frame.ts:36-56` | `frame.orderBy(...)`, then paging is an in-memory `vector.slice` — not an ES `from`, not a plan node |
| QPL `orderBy` | `TableOrderByNode` | `frame.orderBy(fields)`, silently SKIPPED when a field is absent (`hasFields`) |
| QPL `limit` | `TableLimitNode` | **`size` ONLY — there is no offset node.** The pipeline truncates; it never pages |

- **Sliced queries REJECT both `sort` and `start`** (`src/search/validation.ts`), so `start` paging
  only runs on the small non-sliced path; `limit`'s OFFSET half has no current plan consumer, so keep
  it but expect no node to emit it.
- **`DataFrame.orderBy` parses `'field:asc'` colon strings** (default asc, 400 otherwise) and has no
  null-placement control, so engine v2 must translate them — and must QUOTE the field.

**Null placement follows `DataFrame`, and it is now decided in ONE place for both packages.**
`Vector.compare` sorts a nil as the SMALLEST value, and that rule matches no engine:

| | ascending | descending |
|---|---|---|
| Elasticsearch (`missing` defaults to `_last`) | last | last |
| DuckDB (`default_null_order`) | last | last |
| PostgreSQL (a null is the largest value) | last | first |
| **`DataFrame` — what we emit** | **first** | **last** |

Since it matches nothing it can never be left to a default, so `NULLS FIRST`/`NULLS LAST` is emitted
on **every** term. **This was a live divergence, fixed 2026-09-21:** `xlucene-translator`'s `toOrderBy`
emitted `x ASC` and let DuckDB's `NULLS_LAST` stand while the frame emitted `x ASC NULLS FIRST`, so the
same user query put nulls at opposite ends of an ascending page depending on which built the statement.
Both now call `dialect.orderBy`, and `test/duck-frame/query-access-spec.ts` pins the agreement by
running a translated statement and `frame.orderBy` over the same rows. A caller who wants the
Elasticsearch answer passes `nulls: 'last'` on the `SQLSort`.

**`orderBy` takes `SQLSortInput[]` — the translator's own sort shape**, so a translated sort goes
straight into a frame. The bare-string form was dropped: it supplied the expression ONLY, so
`'bytes DESC'` became `bytes DESC ASC NULLS FIRST`, and a footgun whose defence is "it throws loudly"
is one the type system should have refused. `SQLSort.order` stays REQUIRED where it is built from
request data — a missing direction there is a caller bug, not a shorthand — and `toSQLSort` applies the
ascending default for a frame's own API, where `DataFrame.orderBy` has always defaulted that way.

**STILL OPEN — the tiebreaker.** With a sort key that has ties (2M rows, 20 distinct values), the same
`ORDER BY bucket LIMIT 10` returned **2 different pages over 20 runs**, and pages 1 and 2 shared
**1,305 rows**; `DataFrame` does not have this because `Array#sort` is stable. **It is a behaviour
regression unless engine v2 appends a unique field** to every sort — the frame cannot, as it cannot
know which field is unique.

**Identifiers are quoted unconditionally, from `@terascope/core-utils`.** `quoteIdentifier` used to
skip anything matching `/^[A-Za-z_][A-Za-z0-9_]*$/`, which every reserved word matches, so a field
named `group` made a frame that **could not be created at all**; the same flaw existed independently in
data-types' `quoteDuckDBIdentifier` for STRUCT members and in the translator's own copy. **Three
identical copies of the same bug, each fixed separately** — so as of 2026-09-21 there is one
definition, in `core-utils/src/sql.ts`, and the other three delegate to it. Safe because DuckDB treats a quoted identifier
case-INsensitively (the opposite of Postgres), and `diffSchema`'s `normalize` strips quotes because
`DESCRIBE` reports members bare. **The asymmetry is by design:** identifiers we generate are quoted
for the caller, but raw SQL the caller writes is theirs to quote (a `group` field needs
`filter('"group" = \'y\'')`).

### JSON EXPORT — `writeNDJSON` and `ndjson()`

The final result goes to S3 as **ldjson**, and DuckDB renders the JSON in C++ rather than through JS
objects. **Its native output is NOT `DataFrame`'s**, so five divergences are corrected **in SQL before
anything is written** (`src/duck-frame/export-json.ts`), generated from the frame's config:

| | `DataFrame` | DuckDB raw | fix |
|---|---|---|---|
| `Date` | `2026-01-10 00:00:00` | ISO8601 | `strftime`, recursively (inside arrays via `list_transform`, inside nested objects) |
| `Long` > `MAX_SAFE_INTEGER` | a string | bare number `JSON.parse` rounds | rendered as a string, inside arrays too |
| a null field | key omitted (`remove_null_fields` defaults **true**, `create-execution-plan.ts:94`) | `"f": null` | `json_merge_patch('{}', ...)` — RFC 7396 deletes nulls and recurses |
| integral `Float`/`Double`/`Number`, `GeoPoint` whole degrees, `-0` | `5`, `{"lat":-90}`, `0` | `5.0`, `-90.0`, `-0.0` | matched |
| non-finite | `null` | bare `Infinity`/`NaN`, which **`JSON.parse` REJECTS** | matched |

- **Cost: 540 ms / 500k rows (~925k rows/s, 402 MB of JSON)** on the 30-field corpus, scaling with row
  WIDTH — 3 fields is 37 ms (13.5M rows/s), 20 fields is 246 ms. The old "72 ms / ~7M rows/s" figure
  is only reachable on a ~5-field row and **must never be quoted as the export's cost**.
- DuckDB's own uncorrected `to_json(row)` is 167 ms, so the corrected projection is 3.2x raw and still
  ~6x faster end to end than `DataFrame` + `JSON.stringify`; the number fixes added 37 ms (7.3%).
- **500/500 lines byte-identical** on the benchmark corpus, pinned against `DataFrame` itself in
  `test/duck-frame/export-json-spec.ts`. `writeNDJSON(path)` and `ndjson()` (streamed, so a caller can
  flush to S3 as it goes) share one projection and produce identical bytes.
- **Two residues, both narrow, both pinned as tests:** `abs(x) >= 1e21` writes `1e21` where JS writes
  `1e+21` (unfixable through the JSON type, which re-normalises any number given to it); and a
  non-finite value loses its KEY in the default mode, since merge-patch uses null as the delete
  sentinel. Both are byte-identical under `@preserveNullFields`.

> Trap: forcing the projection with `count(*)` reported 500k rows in 0 ms at 1.5 billion rows/s — the
> optimiser discarded it, so no JSON was built. Use `sum(strlen(...))`.

### DATE + TIMEZONE — the defect, FIXED 2026-08-17

**The bug:** `DuckDBTimestampValue.toString()` is zone-less (`'2026-08-14 01:02:03.456'`), every date
primitive coerces it by stringifying, and `new Date(<zone-less>)` parses as MACHINE-LOCAL — so every
date UDF's INPUT drifted by the host's UTC offset (0 under UTC, +4 h New York, −9 h Tokyo). It
corrupted **13 of 16** date functions whatever they returned, and `isAfter`/`isBefore`/`isBetween`
**flipped** between `TZ=UTC` and `TZ=America/New_York` on identical data and an identical query.

**The fix:** `makeInputConverter(type)` in `duck-values.ts` — the mirror of `makeValueConverter` —
applied by `createScalarFunction` keyed off `spec.parameter`, handing a `FieldType.Date` function
`Number(value.micros / 1000n)` (epoch millis, what `DateVector` itself holds, no parse per row). The
structural hole was that the output side had a converter and the input side had none; blast radius
went 13-of-16 to 2, and those 2 are the offset-display question below.

- **Regression-guarded** in `test/duck-frame/date-udf-spec.ts` (11 tests) by asserting the JS **type
  and value** the function receives, because jest caches `TZ` at VM startup and under UTC the drift is
  zero. Reverting the one-line wiring fails 2 tests under UTC, checked.
- **Date is the ONLY type this hurts:** `Long`→`BigInt`, `IP`/`Keyword`/`Text`→`String`,
  `Double`/`Float`/`Number`→`Number`, `Boolean`→`Boolean`, array element→unwrapped scalar, and
  `GeoPoint` **throws at registration** (loud, not silent).
- **NOT affected: the non-UDF path** — ingest → storage → SQL (`date_trunc`) → ldjson export is
  byte-identical under UTC, New York and Tokyo, because ingest stores epoch millis and the export uses
  `strftime` on a naive TIMESTAMP.
- **Pre-existing in BOTH engines:** `isFriday` and friends are locale-sensitive by design, so QPL
  day-of-week results already depend on the worker's TZ. Pin the worker's timezone if reproducibility
  matters.
- **The DuckDB session timezone is never pinned** (`configureDuckDatabase` sets `tempDirectory`,
  `maxTempDirectorySize`, `memoryLimit`, `threads` only), so `SET TimeZone='UTC'` becomes mandatory the
  moment timezone work moves into SQL.

**STILL OPEN: the offset question, separate from the defect.** `setTimezone`/`toTimeZone`/
`toTimeZoneUsingLocation` return a `DateTuple [millis, offsetMinutes]` and `toTimestamp` keeps only
the millis, so `setTimezone({timezone: 120})` gives `2026-08-14T01:02:03.456Z` where `DataFrame` gives
`2026-08-14T03:02:03.456+02:00` — **the same INSTANT**, losing only the user's display directive.

| option | verdict |
|---|---|
| **1. render it in SQL** | `strftime(ts + INTERVAL 120 MINUTE, '%Y-%m-%dT%H:%M:%S.%g') \|\| '+02:00'` is **byte-identical to `DataFrame`**, no UDF, no storage. Best for `setTimezone`, whose numeric offset is a column constant |
| 2. `output_type` → String | exact parity for all three (how `formatDate` already escapes this), but the field stops being a Date so a later sort is lexicographic — wrong across mixed offsets |
| **3. companion offset column** (`created` + `created__offset`) | the only option that handles `toTimeZoneUsingLocation`, whose offset is genuinely per-row. Every projection must thread the second column |
| 4. `STRUCT{millis, offset}` | rejected — every SQL date function, comparison and ORDER BY would unwrap `.millis` |
| 5. `TIMESTAMPTZ` | rejected — renders in a SESSION zone, not a per-value offset |

**Option 3 is implementable in pure SQL and is unblocked:** `date_diff('second', ts, (ts AT TIME ZONE
zone) AT TIME ZONE 'UTC')` is per-row and DST-aware with the zone coming from a COLUMN, verified on
1.5.5 for EST/EDT (−18000/−14400), Kolkata (+19800) and Lord Howe (+37800). Shifting between zones is
`(naive AT TIME ZONE zoneA) AT TIME ZONE zoneB`; details in `research/sql-function-coverage.md`. Note
for options 1 and 2 that `toTimeZone('America/New_York')`'s offset is NOT constant (EDT vs EST), which
makes it a case for the SQL-vs-UDF dispatch descriptor.

### INGEST — multi-slice, concurrency, and the failure contract

Accumulation is **worker-side, from Parquet** (§0.0). Jared rejected the first API
(`DuckFrame.empty()` + `appendParquet()`) on all three counts — a new frame is already empty, two
methods to add data is one too many, and the frame should own its storage.

- **`frame.append(source, opts?)` is ONE method** — `{records}` on the api-server, `{parquet}` on the
  worker — and appending to a relation **promotes it to a table in place**, the only mutation of
  `this`.
- **Appends are ATOMIC**: a DuckDB appender participates in the connection's transaction, so ROLLBACK
  removes rows it had already flushed and a bad payload cannot corrupt what is already assembled.
- **`INSERT ... BY NAME`, not positional** — a plain `INSERT ... SELECT *` FAILS when a payload's
  column order differs, and separate api-server responses cannot be trusted to agree.
- **`AppendError` says what SURVIVED** (`rowsRemaining`, counted after the rollback, failure path
  only); `fromRecords` deliberately does NOT wrap, because it is one-shot and its contract is to throw
  what `DataFrame` throws.
- **`frame.info()`** returns `{ name?, kind, isMaterialized, isOrdered, database, columns, rows, sql,
  appends }`, counting SUCCESSFUL appends only. Spec: `multi-parquet-spec.ts`, 23 tests.

**CONCURRENT APPENDS: the bug was that `BEGIN`/`COMMIT` ran on the process-wide SHARED connection**,
so a second concurrent `BEGIN` threw, its `ROLLBACK` discarded the FIRST append's rows, and the
connection was left poisoned for every later statement on any frame. **Fix: every `append` takes its
own connection** — reverting it fails 5 of 23 tests; 10 concurrent appends into one table then succeed
with no write conflict.

**Throughput, 1M rows / 20 payloads** (`tools/bench/append-ingest.mjs`, darwin/14 CPU):

| | time | rate |
|---|---|---|
| producer: `fromRecords` + `writeParquet` | 1,137-1,194 ms | ~850k rows/s |
| worker: sequential `append` ×20 | ~350 ms | ~2.9M rows/s |
| worker: CONCURRENT `append` ×20 | **118-145 ms** | ~7-8.5M rows/s |
| worker: ONE `append`, all 20 paths | **78-90 ms** | ~12M rows/s |
| records `append`, 200k rows | ~195 ms | ~1M rows/s |

Worker ingest is **7-30% of producer cost** and is not the bottleneck: coercion is the expensive half
and happens ONCE, on the producer, and transaction overhead is negligible so atomicity is free.
**Payload SHAPE dominates** — 2M rows takes 164 ms as ONE payload and 2,798 ms as twenty (17x),
consistent with DuckDB parallelising per 122,880-row group, so handing several landed payloads to a
single `append({ parquet: [...] })` is worth more than the checkpoint is.

> **DO NOT BENCHMARK THROUGH JEST** — the same workload reports ~4x worse (swc, module registry,
> coverage). An earlier version of that table said 205k rows/s for the producer; standalone it is
> ~850k.

**INGEST COST, 500k × 30 columns** (`tools/bench/ingest-breakdown.mjs`): `coerceToType` alone is
1,232 ms and **both engines pay it**; `DataFrame.fromJSON` is 2,140 ms and `DuckFrame.fromRecords`
2,931 ms. So the addressable gap is **791 ms** and a perfect ingest could not beat 1,232 ms.

| at parity or better | ~1.2x | **the losses** |
|---|---|---|
| **Date 0.86x**, Date-as-ISO 0.94x, Boolean 0.95x, Short 0.98x | Long 1.19x, Date[] 1.19x, Double 1.21x, Integer 1.23x, IP 1.34x | **Keyword 3.45x**, **Keyword[] 3.34x**, GeoPoint 1.88x, Integer[] 1.55x |

**This kills the bulk-buffer optimisation for INGEST.** `vector_get_data`/`copy_data_to_vector` (in
`@duckdb/node-bindings`, NOT `node-api`) work only for fixed-width types, and every fixed-width type
is already at 0.86-1.23x — the losers are exactly VARCHAR and nested LIST/STRUCT, which a raw buffer
cannot touch. Strings cost what they do because every JS string is transcoded UTF-16→UTF-8 into
DuckDB's string heap where `DataFrame` keeps a reference; that is paid once on the tier with headroom
and buys 23x on serialize and 34x on the worker's read.

**FAILURE CONTRACT: matches `DataFrame`** (settled 2026-08-14) — strict mode (the default) fails FAST
on the first bad value, and a failed ingest **leaves NO table behind** (the old code orphaned a fully
populated table no caller could reach, a resource leak as well as a parity nit). `mode: 'lenient'`
stays as the opt-in that nulls the value and collects every failing field with counts and examples.

**CONCURRENCY: the shared connection is fine for everything except streams.** Probed at 4 tables ×
20k rows: concurrent ingest (shared or per-connection), ingest during a stream, a throwing ingest
beside a healthy one, a query while an appender is open, and two appenders on the same table all
behave correctly. The only per-connection hazard is an open **streaming result**, which fails
SILENTLY with a short result (500k rows became 100k) — which is why `rows()`, and only `rows()`, takes
its own connection.

### THE CHECKPOINT

DuckDB only compresses at checkpoint; uncompressed means flat vectors, so a UDF runs once per ROW,
and after a checkpoint low-cardinality columns are `DICT_FSST` and the UDF runs **once per dictionary
entry per row group**.

**TRAP 1: a plain `CHECKPOINT` after the ingest path SILENTLY DOES NOTHING.** Deterministic at 1M and
2M rows over 20 sequential, fully-awaited Parquet appends: it returns in 0 ms with all 2,682 segments
still `Uncompressed`, and `FORCE CHECKPOINT` behaves identically.

| after the appends | then `CHECKPOINT` |
|---|---|
| nothing / wait 2 s / `SELECT 1` / `count(*)` / `BEGIN;COMMIT` / `DELETE WHERE false` | 0 ms, **no-op** |
| **another `append()`** | **145 ms**, 2,682 → 11 uncompressed |
| **a one-row `INSERT`** | **134 ms**, 2,682 → 17 |
| **`CREATE TABLE _x(a INT)` + `DROP TABLE _x`** | **132 ms**, 2,682 → 10 |

**So `frame.checkpoint()` must ARM and VERIFY:** arm with the throwaway CREATE/DROP (0 ms), then check
`SELECT count(*) FROM pragma_storage_info('<table>') WHERE compression = 'Uncompressed'` before and
after and fail loudly if it did not fall. Without verification there is no way from outside to tell a
checkpoint from a no-op. Evidence: `tools/probe/checkpoint-noop.mjs`, `tools/bench/checkpoint-cost.mjs`.

**TRAP 2: DuckDB auto-checkpoints during ingest and it is a loss.** `checkpoint_threshold` defaults to
16 MiB, and at some payload shapes a COMMIT inside `append` triggers one, charging compression to
ingest AND leaving a half-compressed table. Which shapes trigger it is not a clean function of payload
size (5k/50k/100k did not; 12.5k/25k did), so **do not reason about when it fires — suppress it and
checkpoint once**: 500k over 20 payloads goes 1,533 ms → **868 ms**, and 500k over 40 goes 1,959 ms →
**903 ms**. That, not the row count, was the "500k anomaly".

**COST, per size** (30-column corpus, 20 payloads, auto suppressed, armed and verified, two agreeing
repeats):

| rows | ingest | CHECKPOINT | ms/1M | immediate repeat | re-ckpt after +5% rows | 3 of 30 columns | DuckDB memory |
|---|---|---|---|---|---|---|---|
| 100k | 149 ms | **90 ms** | ~900 | 0 ms | 5 ms | 6 ms | 64 → 14 MB (4.7x) |
| 500k | 684 ms | **148 ms** | 297 | 0 ms | 50 ms | 7 ms | 316 → 62 MB (5.1x) |
| 1M | 1,341 ms | **156 ms** | 156 | 0 ms | 101 ms | 8 ms | 610 → 121 MB (5.0x) |
| 2M | 2,731 ms | **324 ms** | 161 | 0 ms | 113 ms | 15 ms | 1,204 → 240 MB (5.0x) |
| 5M | 1,586 ms | **1,042-1,285 ms** | 208-257 | 0 ms | 402 ms | 32 ms | 3,152 → 588 MB (5.4x) |
| 10M | 1,870 ms | **1,512-1,593 ms** | 151-159 | 0 ms | 155 ms | 70 ms | 6,139 → 1,188 MB (5.2x) |

- **~80 ms fixed plus ~150-250 ms per 1M rows** at 30 columns, and **memory falls 4.7-5.4x at every
  size** — for a 64 GB worker that is the difference between spilling and not.
- **Arming and an immediate repeat are both free**, so a defensive extra call costs nothing; cost
  tracks **BYTES, not rows** (the same rows over 3 of 30 columns is 5-73 ms).

**CADENCE, reconciled across three sessions.** Cost is per-CHECKPOINT, so cadence is the whole
question: **never during ingest is fastest, ~1M is nearly free, below ~500k is ruinous** (every 250k
doubles-to-triples ingest). The reason to checkpoint during a long ingest is **footprint, not speed** —
on a file-backed 10M-row stream ingest is flat at 82.4-85.9 s across every cadence, while deferring to
the end costs **18% more RSS (6,053 → 7,383 MB) and 20% more disk (1,188 → 1,486 MB)**; suppressing
auto-checkpointing altogether is 1.45x on append but costs 3.6x disk and 1.44x RSS. Pick the coarsest
cadence that keeps peak footprint inside the container.

**STRATEGY, 5M rows / 20 payloads, all five verified to return identical answers:**

| strategy | ready | transform | udf calls | DuckDB memory |
|---|---|---|---|---|
| in-memory, no checkpoint | 1,647 ms | 1,025 ms | 5,000,000 | **3,152 MB** |
| **in-memory, ONE checkpoint at end** | **2,618 ms** | **261 ms** | **3,130** | **589 MB** |
| in-memory, checkpoint every 5 payloads | 3,328 ms | 260 ms | 3,125 | 608 MB |
| file-backed, default (auto-checkpoints) | 5,559 ms | 1,124 ms | 3,180 | 580 MB |
| file-backed, auto off + one at end | 6,473 ms | 1,590 ms | 3,130 | 579 MB |

**A file-backed master is worse on every axis** — compressed-in-RAM beats compressed-on-disk, so do
not move the master table to a file. Two further traps: a `CHECKPOINT` during concurrent appends
returns in 111 ms and does nothing (rows in open transactions cannot be compressed), and payloads
appended AFTER a checkpoint arrive uncompressed (13,540 → 213,540 UDF calls), healed by a
re-checkpoint.

**PAYBACK IS PER-PLAN, NOT A DEFAULT** (69 cases at 100k/1M/5M, `CHECKPOINT=0` vs `=1` differenced by
`tools/bench/checkpoint-payback.mjs`; row counts agree on every one):

| case | 100k | 1M | 5M |
|---|---|---|---|
| transform (array column) | 1.5x | 4.6x | **10.4x faster** |
| validation (isIP) | 1.5x | **7.8x** | 2.2x |
| transform (toUpperCase) | 1.2x | 3.1x | **4.8x faster** |
| 5 transforms + filter | 1.0x | 2.4x | **4.0x faster** |
| group by 1 key + sum · filter (1 of 5) | 2.3x · 2.1x | 1.6x · 1.6x | 2.9x · 2.3x |
| group by 2 keys + 3 aggs | 1.8x | 1.2x | 1.3x |
| join / ldjson / export / append / ingest | ~1.0x | ~1.0x | ~1.0x |
| **sort (2 keys)** | 1.0x slower | 1.3x slower | **1.4x slower** |
| **sort + limit (top 1,000)** · **page (limit 1,000)** | 1.2x slower | **2.3x · 2.8x slower** | 1.6x · 1.3x slower |
| **dedup (all columns)** · **read from the wire** | 1.0x · 1.0x slower | **1.8x slower** · 1.0x slower | 1.1x · **1.6x slower** |

1. **UDF-bearing transforms are where it pays**, and more as data grows (2.95 s → 283 ms at 5M against
   a 976 ms checkpoint, so one pass repays it).
2. **Sorts, top-N, paging and dedup get WORSE, up to 2.8x** — nothing there benefits from a
   dictionary, so compression only adds decompression to a scan.
3. **SQL emission and the checkpoint are substitutes, and emission is the better buy**: those 3-10x
   wins exist *because* the transform is a per-row JS UDF, and emission costs no 1-second tax and does
   not slow sorts down.

> Precision caveat: `RUNS` is 2 at 1M and **1 at 5M**, so anything within ~1.2x is single-sample
> noise — which covers most of the "slower" rows for join, export, append and ingest.

### UDFs — vectorized, single-threaded, and what they cost

1. **Registration is INSTANCE-wide**, so a function registered on one connection is visible to the
   private one each `rows()` stream opens; without this, UDFs and streaming would be incompatible.
2. **DuckDB DOES call a UDF with NULL arguments and data-mate never does**, so the wrapper skips nulls
   by default with `callWithNull: true` to opt back in.
3. **Two type mappings exist and must agree** — `DataType.toDuckDB()` gives type STRINGS for DDL in
   data-types, registration needs the binding's type OBJECTS, so `scalar-function.ts` carries the
   object map and `duckDBTypeObject` **throws** for STRUCT and JSON rather than guessing. `diffSchema`
   catches them drifting.

**A registered UDF requires `instance.closeSync()` or the process never exits** — `disconnectSync()`
alone is not enough, and `destroySync()` on the function makes no difference.

**A JS UDF is single-threaded; SQL is not** (5M × 30 columns, 41 row groups, `cores` =
`process.cpuUsage()/wall`, `tools/bench/udf-threads.mjs`):

| shape | t=1 | t=4 | t=14 | cores@14 |
|---|---|---|---|---|
| passthrough (30-col write) | 2,484 ms | 559 ms | 606 ms | 6.0 |
| sql ×1 (`upper`) · sql ×5 | 2,464 · 3,644 ms | 588 · 962 ms | **251 · 403 ms** | **10.7 · 9.2** |
| udf ×1 · udf ×5 | 3,650 · 10,875 ms | 1,080 · 7,372 ms | 1,055 · **7,357 ms** | 4.2 · **1.8** |
| udf ×1 aggregated (no write) · sql ×1 aggregated | 994 · 55 ms | 959 · 15 ms | **997 · 8 ms** | **1.0** · 8.8 |

**The 18x and 125x from that aggregated pair are real FOR THIS SYNTHETIC and do not generalise** — the
same five-function shape on the real corpus is **2.98x at 1M**. Quote them only as "what the UDF
boundary costs when a query is nothing but UDFs"; the plan around a UDF still parallelises (udf ×1
uses 4.2 cores), so it is Amdahl, not a flat tax.

**The cost is marshalling, not our code** (2M rows, aggregated): an **empty** callback is
**178 ns/value**, with our converters and the real function 198 ns, three string ops 208 ns, native
SQL **1-2 ns**. Converter micro-optimisation therefore cannot matter (~10%), and the cost is flat
across 500k/2M/5M, so per-value rather than per-chunk.

**THE COST OF A UDF IS LINEAR — THERE IS NO THRESHOLD.** An earlier "parallelism cliff between 2 and 3
UDFs" was an artefact of applying five different functions to five columns of 100k/2M/5/4/2M
cardinality (the increments tracked column cardinality, not UDF count); with the variable isolated
(same function, same column, N registrations, 2M rows) the cost is **~342 ms per UDF = 171 ns per
value**, dead linear from 1 to 6, and **parallelism collapses at the FIRST UDF** (9.2 cores at 0 UDFs,
1.5 at one).

- That 171 ns independently reproduces the 178 ns/value marshalling figure measured by a different
  method, which corroborates both. Each promotion removes a fixed ~171 ns per value independently of
  the others — no cliff to get over, and no bonus for finishing.
- **Mechanism, from primary sources** (`research/client-udf-parallelism.md`): node-neo hands each call
  to a `TypedThreadSafeFunction` created with ONE thread and blocks the calling DuckDB worker, while
  Rust and Java genuinely parallelise — so this is a Node-binding property, not a DuckDB one.

- **PARQUET DICTIONARIES ARE SCOPED TO THE ROW GROUP, NOT THE FILE** (1M rows, one VARCHAR): 100
  distinct values costs 0.9 bytes/row, 122,880 costs 4.0, and 1,000,000 costs only 4.3 — so nearly all

|---|---|---|---|
| uncompressed | 2.890 GB | **37 ms** | **1.030 GB** |
| snappy | 1.469 GB | 46 ms | 1.165 GB |

### THE REMAINING CORE GAPS

Derived by asking what a query must PRODUCE (§0.1), not by mapping `TableAction` onto methods.
Measured against the real API, `require`, nested-path/`deepSelect`, `_skip_if_empty` pruning and
correlated `unnest` are **already expressible** with `filter()` and `select()` — they were never gaps.

1. **`unnest` / expand-values** — the correlated shape already works as a `select` expression; the
   **stacked** shape needs `UNION ALL`.
2. **`deepSelect` + `_skip_if_empty`** — decide how nested extraction and empty-object pruning are
   expressed, then confirm the engine can build it.
3. **The date/timezone offset column** — unblocked; see the options table above.
4. **The SQL-vs-UDF dispatch descriptor** for the 205 functions, declared ON the function config.

**`expand_values` with `corelate_values_across_fields: false` is NOT a cross product** — an earlier
claim made from the interface comment plus a DuckDB probe, without reading `expand-values.ts`, whose
`calculateSize` decides it:

| flag | rows per input row | shape |
|---|---|---|
| `true` (search / `qpl_context`) | `max(len)` | **positional zip**, short lists NULL-padded — several `unnest()`s in ONE select |
| `false` (`@expandValues` on individual fields) | **`sum(len)`** | **stacked**: each field expands into its own block of rows, the others NULL there |

So `false` is vertical concatenation (`['a','b','c']` + `[1,2]` gives **5** rows, not 6), expressible
as `UNION ALL` of one projection per field — **no FROM-clause extension is needed**. Parity detail:
when every expanded list is empty `calculateSize` forces the count to 1 so **the row SURVIVES with
nulls**, where a plain `unnest` drops it; the fix is
`unnest(CASE WHEN x IS NULL OR len(x) = 0 THEN [NULL] ELSE x END)`.

**Deferred, not core:** `UNION ALL` of relations as a general capability, `sample`, `mergeBy`, paging
tiebreakers, the shelved data-mate defects.

### THE 205 FUNCTIONS ARE GQL DIRECTIVES THE USER TYPES

`qpl-engine/src/v3/type-defs/directives.ts` walks `functionConfigRepository`, filters by
`isFieldOperation`, and emits `directive @<name>(<args>) on FIELD_DEFINITION | FIELD` for every
function **and every alias**, so function drift is a public API break. **The aggregation names are
directives too** — `@hourly`, `@daily`, `@monthly`, `@yearly`, `@sum`, `@avg`, `@min`, `@max`,
`@count` — so v2 must map those names onto SQL and renaming one is a public break.

### HOW TRANSFORMS AND VALIDATIONS WORK — the machinery to reproduce

Sources: `src/adapters/data-frame-adapter/index.ts`, `src/builder/Builder.ts`, `src/column/utils.ts`,
`qpl-engine`'s `run-pipeline/operations/column-nodes/index.ts`.

```
Column(vector, configA)
  -> fnDef.output_type(configA, args) = configB   <-- THE TYPE CHANGES HERE, mid-plan
  -> Builder for configB
  -> for each value: builder.set(fn(value))       <-- the Builder ENFORCES configB
  -> Column(newVector, configB)
```

1. **`output_type` changes the field config mid-plan**, and the Builder for the NEW config coerces the
   result — which is why `duckFrameAdapter` returns `outputConfig`; thread it into the next step.
2. **Validations NULL the value and keep the row; transforms THROW**, aborting the query.
3. **A transform sees non-nil values only** unless the function opts into nulls, which is the source of
   the UDF null-skipping rule.

**The adapter mirrors `dataFrameAdapter` deliberately:** args bound once via `create()` (**per-row args
unsupported** — a UDF's inputs are columns), result type from the function's own `output_type`,
`ProcessMode.NONE` emitting the bare column, `INDIVIDUAL_VALUES` on an array column becoming
`list_transform(col, lambda x : udf(x))`, validations emitting `CASE WHEN pred THEN col ELSE NULL END`,
and an `accepts` mismatch throwing for a transform and NULLing for a validation. Aggregation is
`select(expressions, config, groupBy)` — an aggregate in SQL is a projection with a GROUP BY, so do not
give it its own execution concept (an `AggregationFrame`-style surface was built and deleted).

**`join(other, { on, select, config, type?, as?, otherAs?, groupBy? })`** aliases both sides, because
frames routinely share column names and a subquery in FROM needs a name; N-way joins chain and stay ONE
statement (tested to 4 levels), with the friction that a column needed at level 4 must be projected
through every level. Two defects found by driving real configs through the adapter: a UDF's JS result
must go through `makeValueConverter` (a `number` into a BIGINT vector throws), and `rows()` leaked
DuckDB value wrappers — fixed with `toPlainValue`, since `rows()` is the OUTPUT path.

**All emitted lambdas use `lambda x : …`, never `x -> …`** (verified 2026-08-24 across
`duck-frame-adapter/index.ts`, `export-json.ts` and `function-configs/numeric/sql-utils.ts`), because
DuckDB v2.0 disables the single-arrow syntax by default and v2.1 removes the `lambda_syntax` flag.

### `DuckContext` AND DATABASE CONFIGURATION

`DuckContext` is **not exported** — databases are cached per path behind an internal `getContext()`,
`closeDuckDatabase(database?)` is the teardown, and `frame.query(sql)` hands out neither connection nor
instance so it cannot route frames between databases. `configureDuckDatabase({ database,
tempDirectory, maxTempDirectorySize, memoryLimit, threads })` issues runtime `SET`s, and
**`tempDirectory` is what makes whole-dataset-plus-overflow work** — without it an over-limit query
fails instead of spilling.

- **Only the exact string `:memory:` is in-memory** — a bare name AND the `:memory:<name>` form each
  write a database FILE into the working directory. Tests need no `database` option, since jest gives
  each test file its own module registry.
- **`frame.query()` is JSON-rendered**, so a BIGINT returns as `'2'`; `rows()` is the native-value path.
- **DuckDB reads `'2GB'` as 2×10⁹ bytes** and reports `1.8 GiB`, so use binary units.
- `DataType.toDuckDB()` lives in data-types as one method per FieldType class, and is **deeper than its
  siblings**: `getGroupedFields` splits on the first dot only, so `GroupType.toDuckDB()` regroups and
  recurses — otherwise a nested object emits a STRUCT with a dotted member name. **Rebuild data-types
  after touching it**; data-mate resolves it to `dist`.
- **A bad argument not to repeat:** "cross-frame joins need both tables in one catalogue, so the shared
  context is load-bearing" defends a design nobody proposed — there is one database per process by
  construction, and a join is a relation over two sources.

### THE PARITY OBJECTION TO SQL DOES NOT HOLD AS STATED

`duckdb-parity.md`'s divergences, and the "11 divergences / 26 of 40 casts" line, were measured against
DuckDB's **default cast** — which proves DuckDB's casts differ from our coercion, not that SQL cannot
express our semantics. Re-tested with deliberate expressions (`tools/probe/sql-semantics.mjs`): **13 of
13 previously-divergent inputs match data-mate exactly.**

| input | data-mate | naive `TRY_CAST` | deliberate SQL |
|---|---|---|---|
| `12.7`, `2.5`, `-2.5` → Byte | 12, 2, -2 | 13, 3, -3 | `TRY_CAST(trunc(v::DOUBLE) AS TINYINT)` |
| `0x10`, `0b11`, `1e3` | 0, 0, 1 | 16, 3, 1000 | `regexp_extract(v,'^[+-]?[0-9]+')` then cast |
| `'y'`, `''` → Boolean | THROW, false | true, null | `CASE … ELSE error('…') END` |
| `1710028800000`, `Mar 10 2024` → Date | parsed | null | `epoch_ms(v::BIGINT)`, `try_strptime(v, [formats])` |
| `01.02.03.04`, `1.2.3.4/24` → IP | THROW | accepted | regex guard + `error()` |

`error()` reproduces a THROW and `try_strptime` takes a LIST of formats — those two unlocked it. **Two
surfaces were also being conflated:** those divergences are INGEST COERCION (string → typed value),
while the 205 functions run AFTER coercion on typed values, so transform parity is a smaller problem.
The genuine residue of risk is JS-flavoured semantics — number formatting at the extremes, JS regex vs
RE2, date format tokens.

**Coverage for the 205** (detail in `research/sql-function-coverage.md`). **Native and in-engine:**
string case/trim/pad/split/similarity; RE2 regex; `md5`/`sha1`/`sha256` (no `sha512`);
`url_encode`/`url_decode`, base64, hex; `error()`; date parse/format/truncate/parts/diff; icu timezone
shifting; `inet` containment (`<<=`, `>>=`), `host`, `network`, `netmask`; JSON extraction and
`json_valid`; the whole `list_*` family.

**NO native equivalent** — the only candidates for a native extension: MAC/EUI, IPv4-vs-IPv6
discrimination, masklen/abbrev/inet_merge, IP↔integer, geohash, index-accelerated radius/KNN,
metric-radius `ST_DWithin` on GEOMETRY (planar only; spheroid variants are POINT_2D-only), JSON Schema
validation, jq-style paths, fuzzy date parsing, non-English month/day names, business-day arithmetic,
and any regex needing **lookahead / lookbehind / in-pattern backreferences** (RE2 rejects all three,
measured).

1. **`ST_Distance_Sphere`/`_Spheroid` take (lat, lon)** — the reverse of `ST_Point(x=lon, y=lat)`. NYC
   to London measures **5,570 km swapped against 8,247 km correct**, and short-radius tests hide it, so
   pin the argument order with a long-distance assertion.
2. **`strptime`/`strftime` formats must be CONSTANT**, not from a column — fine for us, since a QPL
   format is a directive argument, i.e. a plan constant. Part names, zone names and JSON paths may be
   per-row.
3. **`@duckdb/node-api` renders TIMESTAMPTZ in the INSTANCE-CREATION zone and ignores `SET TimeZone`**,
   so **always format server-side** (`strftime(ts AT TIME ZONE 'UTC', …)` or `epoch_ms(ts)`). The
   export projection already does; do not regress it.

Minor: `duckdb_timezones()` does not exist (it is `pg_timezone_names()`, 638 rows); `spatial` does NOT
autoload, though `icu` and `inet` do.

## DO NOT

- **Do not reintroduce JSON.** No `read_json`, no ndjson staging, no `JSON.stringify` of records — the
  ES client returns parsed objects and the wire carries Parquet. A `read_json`-based SQL coercion layer
  was built, measured as a net loss, extended for ten more increments on sunk cost, then deleted
  (~2,000 lines); read `ingest-findings.md`'s STOP block.
- **Do not reimplement field semantics in SQL.** Use `coerceToType` and the `core-utils`/`ip-utils`/
  `geo-utils` primitives, in a UDF if needed; reimplementing produced 11 divergences plus three
  null-handling bugs that `callIfNotNil` makes impossible.
- **Do not gzip the transport** — Parquet zstd is smaller and ~50x cheaper to produce.
- **Do not mutate a frame's table in place.** Relations read it by name, so an UPDATE/DELETE/INSERT
  would silently change every derived frame; appending while assembling is the one legitimate case.
- **Do not add API on spec.** `toArray()` was added because `DataFrame` has one, spaces never calls it,
  and it carried a bug for three increments; `getColumn` is deliberately absent because all 7 uses in
  spaces extract a resident JS vector, which cannot port.
- **Do not pursue mass-batching of distinct join keys**, and **ignore partitions** — an unused feature
  that may be removed.

## Verified DuckDB facts (probes in `docs/tools/probe/`)

- **Alpine/musl works.** `node:24-alpine`: import 249 ms, instance init 112 ms, 71.9 MB in-image, with
  `icu`/`parquet`/`json` statically linked; **`nanoarrow` has no musl build**, so community extensions
  are unavailable.
- **Nothing runs until `create()`** — no daemon, no socket, no readiness probe (import +45 MB,
  `create()` +33 MB).
- **The bindings expose a bulk-buffer path** (`vector_get_data`, `copy_data_to_vector`, …), verified
  both directions including validity masks. It is a bulk memcpy, **not zero-copy**.
- **Arrow is off the table** — all 20 Arrow C-API functions are commented out in the Node bindings, and
  `scan_arrow_ipc` needs raw pointers pure JS cannot produce.
- **RULED OUT: Parquet → `/dev/shm`** — the numbers behind it were consumer-side only and the premise
  was wrong, since the input is already-parsed JS objects, not bytes. **Do not revisit.**
- **RULED OUT: `read_json` as the ingest mechanism** — `read_parquet` is 27 ms/1M against
  `read_json`+coercion at 263 ms/1M, and DuckDB's own cast rules diverge from the DataType config on 26
  of 40 probed inputs.
- **Do not let DuckDB make the HTTP call.** It works, but httpfs is a dumb GET while the real reader
  has auth, POST bodies, slicing, retries and backpressure.
- **Joins**, 1M × 20M at 1M distinct keys: flat 555 ms, per-parent `fetch:10` 1,322 ms, `@first`
  870 ms, LEFT JOIN 495 ms. ⚠ **A pure DuckDB probe over synthetic tables, produced at the INVALID
  6GB/2-thread envelope** — re-run `tools/bench/join-shapes.mjs`, whose defaults are now the worker's.

## Decisions already taken by Jared and his boss

- The DuckDB frame is **its own thing with its own API**, a **new subfolder inside
  `packages/data-mate`** — not a new package, not a backend swap behind `DataFrame`.
- `DataFrame` and the QPL engine are **frozen**, a **spaces engine v2** will target the new frame

## Spaces architecture, as verified

- **One Docker image**, three roles by command: `api-server`, `task-runner-origin`,
  `task-runner-child`.
- **Synchronous queries run entirely in the api-server**; the forked `spaces_qpl_worker` (64 GB)
  handles `long_running=true`, and the intent is to make that the default.
- **The reader never talks to Elasticsearch** — it POSTs to the spaces search API — and
  non-long-running queries have no row limit, just a 2-minute wall clock.
- **Joins fan out today**: one child search per parent row, mitigated by a 10,000-entry LRU that high
  cardinality defeats. That is the motivation for a real SQL join.

## Appendix B. Environment traps — still current

- **A PostToolUse formatter fights the repo's eslint**, rewriting whole files to 2-space/double-quote
  where the repo is 4-space/single-quote, and `eslint --fix` does not fully undo it. The hook matches
  `Edit` only, so **use `Write` or a script for `.ts`/`.js`** and check `git diff --stat` — a large
  diff for a small change means formatting churn.
- **Runner import errors usually mean a stale `dist`** (`pnpm build` at the repo root). **Use
  `ts-scripts`, never jest directly** — the flag is `-- --testPathPatterns <p>`.
- **Jest ignores mid-process `TZ` changes** (the VM context caches it at startup), which is why D5's
  timezone half has no test; reproduce it outside jest.
- **`timeout` does not exist on macOS** — it exits 127, which reads as a failing script — and **`node
  -e` leaves `process.argv[1]` undefined**, which breaks `isExecutedFile` and made 18 healthy bench
  files look broken.
- **Do not benchmark through jest** — ~4x pessimistic (swc, module registry, coverage).
