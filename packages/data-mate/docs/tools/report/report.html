Parquet or a table?

The worker receives every search slice as a Parquet payload. It can append them into a DuckDB table, or leave the bytes alone and query them where they land. This is the measurement behind that choice — five scales, fifteen query shapes, and the S3 round trip that previous rounds left at zero.

corpus 30 columns, every field type scales 100k → 100M rows battery 15 query shapes machine 14 cores · 36 GB · memory_limit 24 GiB DuckDB v1.5.5 via @duckdb/node-api

The recommendation

  1. Keep the payloads as Parquet and query them in place. Do not append into a table. Landing bytes is 188x faster to ingest, and a table only repays its cost after 272 queries on aggregation-shaped work. These jobs aggregate rarely.
  2. The query penalty for that is 1.38x, and it uses 3.2x less peak memory — plus it leaves the buffer pool essentially free, which is what lets concurrent jobs coexist. One caveat, precisely bounded: a wide SELECT * … ORDER BY … LIMIT over Parquet needs ~1 GiB of scan headroom regardless of dataset size, and fails rather than degrading if it does not get it. Projecting only the needed columns removes it. Section 1 has the mechanism.
  3. Do not hold tables in memory. At every scale from 100k to 100M, a file-backed table queries within noise of an in-memory one, while costing 73.9 s to load and gigabytes of RAM to keep.
  4. Size slices, not files. Query cost tracks row groups, not file count: 10 files and 100 files are identical. Only consolidate if slices fall to ~10k rows, and target ~2M rows per object when you do.
  5. On S3, latency raises the floor for every layout equally — it does not punish object count the way we predicted. A request-count model over-predicts the penalty by ~22x because DuckDB prunes objects and fetches concurrently. Turn the three httpfs caches on anyway; they are off by default and cost nothing.

Where the decision actually sits

Records become columnar exactly once, on the producer, and the wire has carried Parquet since that was settled. The worker therefore never coerces anything — it receives finished bytes. That is what makes this a real choice rather than a tuning exercise: the worker already holds a queryable file, and appending means decoding and re-encoding data that is already in the right shape.

The query battery

Every measurement in this report runs the same fifteen queries against whatever is being compared, so a format, a layout and a storage choice are all judged on identical work. Two terms are used throughout and are worth pinning down before the results:

"Full battery" is the sum of the warm times of all fifteen queries below. It is a single number for "how does this option feel across a realistic mix of work" — useful for ranking, but it hides its own distribution.

"Cheap queries" is the five marked cheap: the ones that are dominated by reading metadata rather than column data. These are where layout and file count actually land. The expensive shapes — quantiles, high-cardinality group-bys — spend their time inside the aggregation and barely notice how the bytes are stored.

"Aggregation-shaped", used in the break-even arithmetic, strips search: top 100 rows. That query is scan-bound rather than metadata-bound and is a disproportionate share of any total, so leaving it in flatters every result that claims a saving.

What it settles

Parquet+zstd costs 1.38x at 100M and never leaves the 1.15–1.44x band anywhere on the ladder. That stability across three orders of magnitude is the useful part: the ratio can be planned against, and nothing surprising appears at scale.

The penalty is also not spread evenly. It falls almost entirely on cheap queries, where reading footers is most of the work; on the expensive shapes the two formats converge — agg: quantiles at 100M is 2.53 s on Parquet against 2.62 s on the native table. A dashboard that runs one aggregation pays nothing for Parquet; a UI firing many small metadata-bound lookups pays the whole ratio.

Everything else is out, and not narrowly. Arrow IPC is 3.9x the disk of native and degrades from 2.1x at 100k to 8.1x at 1M, because it carries no row-group statistics and every query full-scans. CSV and NDJSON sit at ~17x and re-parse the file on every query.

The memory axis — and a correction to this report

An earlier version of this page claimed a Parquet view holds ~65x less memory than a native table. That claim was wrong, and it is worth explaining why rather than quietly dropping.

It came from sum(memory_usage_bytes) in duckdb_memory(), which reported 172 MB for the Parquet view against 11.0 GB for the table. The tell that something was off: the native figure equalled the database file size to four decimal places at every scale from 100k to 100M. A metric that tracks file size is not reporting a fixed requirement.

Probing it (probe/memory-metric.mjs, running each case in its own process and varying memory_limit) gives three corrections:

  • It is not the file size. The Parquet file at 100M is 2.7 GB on disk. The small number was always memory, never storage — but the two sat close enough together in the text to invite exactly the confusion you would expect.
  • Buffer-manager residency is elastic, not a requirement. Given room, DuckDB caches the whole table, so the metric converges on the file size. Squeeze memory_limit and the identical workload completes holding a fraction of it.
  • Peak process RSS is the number that decides whether a job fits, and by that measure the gap is far smaller than 65x.

Fourteen of the fifteen shapes are fine on Parquet down to 128 MiB — every filter, every aggregation, every projection. The fragile one is a single shape:

A wide top-N. Two others (agg high-card, count distinct) fail only at the extreme 128 MiB and are not a practical concern.

The law, and what to do about it

A Parquet scan's working set is threads × row-group size × columns projected — not dataset size. At 14 threads, DuckDB's 122,880-row group and all 30 columns, that needs somewhere between 512 MiB and 1 GiB, and it needs exactly the same whether the table holds 10M rows or 100M.

Why the native table survives where the view does not: the table keeps a large evictable reserve of cached clean pages (1.1 GB of BASE_TABLE at a 2 GiB limit), which DuckDB drops instantly when an operator needs room. The Parquet view caches almost nothing — EXTERNAL_FILE_CACHE peaked at 17 MB — so there is no reserve to give back, and the allocation simply fails.

Three ways to remove it, in order of preference: project only the columns the query needs (QPL knows them — SELECT * is the worst case and rarely what a user asked for); cap threads (4 is sufficient at 256 MiB); or budget ~1 GiB of headroom per concurrent query, which on a 64 GB worker is not a constraint for one job and is very much one for fifty.

02

Appending a table against querying the payloads

Where is break-even, and what decides which side of it you are on?

All three options receive the same bytes, so the producer leg is excluded from every one of them — counting it would add the same constant three times and change no comparison. What is measured is only what the worker does with a payload already in hand.

"ready" includes the checkpoint that has to happen before a table is in its steady-state compressed form. Landing needs no such step.

What "break-even" means here, and why it is the deciding number

Building a table is an investment: you spend time once, up front, and get a faster query every time afterwards. Whether that is a good trade depends entirely on how many queries you actually run.

Worked, with the 10M numbers from the table above. Appending the payloads into a table instead of just landing them costs an extra 20.1 s, once. In exchange each query gets 74 ms faster. Dividing one by the other: you need 272 queries against that dataset before the table has paid for itself. Query it fewer times than that and appending was pure loss — you spent 20.1 s to save less than that.

So the question is not "which is faster" — it is "how many times will this dataset be queried". These jobs are documented as append-dominated and aggregating rarely, which puts the real number in the single or low double digits.

Reading the break-even honestly

The full-battery column is flattered by top 100 rows, which is scan-bound rather than metadata-bound and is a large share of the total saving. Strip it and the aggregation-shaped break-even roughly doubles or triples. At 10M rows that is 272 queries against one dataset before appending pays for itself. A job that runs a handful of aggregations never reaches it.

The second result matters as much as the first: if you do want a table, build it once at the end — never by appending per payload. At 100M, appending incrementally takes 4.3 min while landing and materialising once produces the same table in 55.1 s — 4.7x cheaper, for a byte-identical result.

Correction to a recorded figure

Our notes record append as 11.3 ms per call, per statement and not per row. That does not reproduce here: at 50k-row payloads the median call is 92 ms, and the sweep above shows the cost tracking payload size almost exactly. Fitting the three sweep points gives 2.0 ms per statement plus 1.88 µs per row — so at a 50k-row slice the per-statement constant is about 2% of the cost and the rest is per-row work.

The practical consequence is the opposite of what the recorded figure implies. If append cost were per statement, batching several payloads into one call would be a large win — our notes claim exactly that. Because it is per row, batching saves only the small constant, and the only way to actually avoid the cost is not to decode the rows at all. That is what landing the bytes does.

03

Tables in memory against tables on disk

Is there a query advantage to keeping the table in RAM?

Both tables are checkpointed before measurement. Without that this would compare a compressed file against an uncompressed memory table and report the compression difference as a storage difference — DuckDB only compresses at checkpoint.

Differences under about 15% are inside single-sample noise at these scales — the point is that there is no consistent direction, not that one wins by a little.

Answer

No — there is no query advantage at any scale. The differences have no consistent direction and sit inside sampling noise. What in-memory does cost is real and one-directional: 73.9 s to load 100M rows against 1 ms to attach the file, plus 11.3 GB of RAM held for the duration.

DuckDB's buffer manager already caches hot pages from a file-backed table, so a resident copy buys nothing it was not doing anyway. This also means the worker is free to let the OS manage the footprint, which is the safer failure mode under memory pressure.

04

Many files against one big file

100 files or 1,000? Ragged sizes? One giant object? And how would that object be produced?

Every layout below holds the same 10M rows and is produced the way the worker really receives them — one object per slice — then consolidated at four different target sizes. Row groups are censused, never inferred, including for the native table.

First: file count is not the unit of cost, and here is the proof

An earlier version of this report published a "µs per file" column. That column was misleading and has been removed, because the file is not what a query pays for. Two of the layouts settle it cleanly:

The decisive pair

as landed: 100 × 100k — 100 files, 100 row groups — answers count(*) in 4.1 ms.
consolidated: ~500k rows/object — 20 files, 100 row groups — answers it in 4.1 ms.

Same number of row groups, 5x different file count, identical cost. If the file were the unit, these could not tie. A query pays for row groups; files are almost free.

That is why the per-file figure looked wrong — it was wrong. Dividing a query's time by the file count produces a number that swings wildly (from ~30 µs across 1,000 files to the entire query time when there is one file) precisely because it is dividing by the wrong thing. Dividing by censused row groups instead gives a near-constant 27–44 µs across every Parquet layout in the table, spanning a 1,000x range of file count.

What that means for consolidation

Because slices arrive below DuckDB's 122,880-row group, each payload becomes its own under-filled row group. Consolidating helps only insofar as it packs those groups fuller — and once the groups are reasonably full, further merging buys nothing:

  • 10k slices are the one real problem. 1,000 objects of 10k rows is 220 ms on the cheap queries against 43 ms for 100k slices — the only layout worth acting on.
  • The realistic jagged mix is already fine. 770 ms on the full battery, indistinguishable from tidy 100k slices.
  • One giant object is not better than twenty medium ones. Every consolidated target — 82 objects, 20, 5, or 1 — lands within a few percent of the others, because they all end up with roughly the same 81–100 row groups. "One big file" has no special property.

How the single object would be generated

Two routes, both measured on the same jagged input:

  • Stream it through — COPY (SELECT * FROM read_parquet([...])) TO one.parquet — 1.69 s.
  • Stage it in a table first, then copy out — 4.35 s, for a byte-equivalent result.

Stream it. There is no reason to stage.

A number I am deliberately not publishing

This run also timed each consolidation target as it was built, but that loop used LIMIT n OFFSET k per batch, which rescans from the start every time and is therefore quadratic in batch count. It produced non-monotonic nonsense — 12.0 s for 82 objects, 3.5 s for 20, 14.6 s for 5 — which measures my loop, not consolidation. Those figures are excluded rather than reported. The trustworthy build number is the stream route above (1.69 s for the whole 10M into one object); measuring per-target build cost honestly needs a single-pass partitioned write, and has not been done.

Correction to a recorded claim

Our notes record that "writing a native table costs LESS than rewriting Parquet", and conclude that consolidating to Parquet is always dominated by materialising. That does not reproduce. Streaming the jagged layout into one Parquet object took 1.69 s; building the native table from the same input took 16.5 s — 9.7x the other way, because the table writes several times more bytes. The recorded result came from consolidating 2,000 tiny payloads, where decode overhead dominates the write. Which is cheaper depends on the input layout; the general claim should be retired.

Local disk against S3

And what happens when the round trip is not zero?

Every remote number we have recorded until now was taken against minio on localhost, where the round trip is sub-millisecond. That isolates protocol and CPU cost, which is a real finding — but it silently sets the term that dominates real S3 to zero. The prediction in our own notes did not hold

Our notes flag real S3 latency as the term that could "collapse every break-even in favour of consolidation", reasoning that Parquet issues 2–5 requests per file and each pays the round trip: 87 objects would then cost 2.94 s at 100 ms. Measured, the same query costs 133 ms — the model over-predicts by roughly 22x.

Two reasons, both visible in the table. Requests do not scale with objects: 87 objects drew only 29.4 requests per query, because row-group statistics prune most objects before they are ever fetched. And the requests that do happen are issued concurrently, so the round trip is paid in parallel rather than in series.

The practical reading is the opposite of what was expected. Latency raises the floor for every layout at once rather than separating them. At 0 ms the three layouts span 4 ms–7 ms; at 100 ms they land within 24 ms of each other. Consolidation is worth 1.22x under latency on this query — real, but nothing like the 8–30x that the zero-latency localhost numbers implied, and not enough on its own to overturn a break-even.

What this does argue for is unchanged: if the worker is going to be latency-bound, the win comes from issuing fewer, larger reads and letting row-group statistics prune — not from chasing object count.

Still turn the caches on

enable_http_metadata_cache, parquet_metadata_cache and httpfs_connection_caching ship disabled. Their benefit here is around 2x on metadata-bound queries at low latency and shrinks as the round trip dominates — less dramatic than an earlier note claimed, but free, one-directional, and previously observed to fix outright connection failures at high file counts. Turn them on.

What this model is and is not

A fixed injected delay where real S3 has a distribution, and no TLS, no per-prefix rate limits, no cross-AZ effects. Report these as "modelled at N ms", never as "measured on S3". What the model does capture faithfully is the term that matters — request count multiplied by round trip — which is why the layouts diverge as latency grows.

Two results, both load-bearing

Compression narrows the SQL advantage but does not collapse it — 9.6x uncompressed against 7.3x compressed at 10M rows. Roughly a quarter of the headline is attributable to measuring on a table nobody queries.

A single unpromoted function dominates a query. Two UDFs among five functions cost 3.1x the all-SQL pipeline. The 17 functions still on the UDF path are not a rounding error — one of them anywhere in a query erases the benefit of the other four running natively.

Bottlenecks and risks this does not solve

The measurements above answer the storage question. These are the things that could still bite, listed because a report that only carries good news is not useful.

R1

This whole decision is a small slice of the end-to-end cost Producing 100M rows on the api-server — querying Elasticsearch, coercing every field, writing Parquet — took 13.6 min. Landing those same bytes on the worker took 6.15 s. So the recommended option is about 0.8% of the pipeline's wall clock, and even the worst option here (4.3 min to append) is only 32%.

That does not make the choice unimportant — it is decided on memory and concurrency, not wall clock, and those are what cap how many jobs a worker carries. But it does mean this report is the wrong place to look for end-to-end speed. If that is the goal, the target is coerceToType on the producer, which is roughly half of that 13.6 min and is the same code on both engines.

R2

Real S3 latency is modelled, not measured The model injects a fixed delay per request; real S3 has a distribution, TLS, and per-prefix rate limits. It was expected to be the term that overturns the recommendation and it was not — but that conclusion rests on the model being faithful in the one way that matters, concurrency of requests. A real bucket under real concurrency is still the measurement to run, and it is the cheapest way to retire the largest remaining assumption.

R3

The spatial extension is a hard ship prerequisite 13 geo functions are promoted to SQL and have no UDF fallback at all — without the extension packaged into the worker image, those queries fail outright rather than running slowly. It does not autoload. inet is the same job, smaller, and does autoload.

R4

Two functions answer differently on the SQL path than the JS path isBase64 and the geo shape predicates deliberately differ from the JavaScript implementation — the SQL is more correct, but "more correct" is still a behaviour change on a public GraphQL directive. These need to be signed off as intentional, or gated, before cutover.

R5

Row-group fill on real payloads is still unknown Everything here uses a synthetic 30-column corpus. The law says cost tracks row groups, and slice sizes decide row-group fill — so a census of real spaces payloads is what says whether any of this currently costs anything. It is cheap to run and has not been run.

R6

Concurrency across jobs is untested, and it is now the biggest open question Every number here is one job on an idle machine; the worker runs several. This is where the Parquet scan reservation stops being academic: it is ~1 GiB per concurrent wide top-N, fixed, so N such queries want N GiB of headroom between them and the ceiling. A single job on a 64 GB worker cannot hit it; fifty concurrent ones can.

Several concurrent queries against one memory_limit is the measurement most likely to change an operational decision, and it has not been run. The mitigation is known and cheap either way — project only the columns the query asked for.

Recommended next steps

1

Adopt "land the bytes, query in place" as the worker's default It is the fastest to ingest, the smallest on disk and in memory, and the simplest to reason about. Keep materialising available as a per-job switch for the rare high-Q dataset.

2

If a table is ever wanted, build it once at quiesce Never by appending per payload — measured 4.7x cheaper at 100M for the identical result.

3

Turn on the three httpfs caches wherever S3 is used They are off by default. Do it before any remote rollout, not after the first incident.

4

Run a row-group census on a real corpus The cheapest remaining measurement, and the one that says whether the layout guidance changes anything in production today.

5

Measure against a real S3 bucket To retire R2. Same bench, real endpoint, several jobs at once — the modelled result says object count matters far less than feared, and that is worth confirming before it is relied on.

6

Package spatial and inet into the worker image A build step, but a blocking one for the geo functions.

7

Never emit SELECT * from the query planner Project only the fields the query actually references. It removes the one Parquet memory cliff outright, and it reduces scan cost on every other shape too. QPL already knows the field list.

8

Re-point optimisation effort at the producer It is the dominant cost in the whole pipeline, and coerceToType is roughly half of it.

Method, and what would invalidate this

One corpus of 30 columns covering every field type, generated from a fixed seed. Every scale builds the native table first and derives every other format from it by COPY, so no generator variation can reach a number. Warm figures are the median of repeats after a discarded first run; cold figures are reported separately in the raw results. Benches were run strictly one at a time — two DuckDB benchmarks sharing 14 cores produce four numbers that are all wrong and none obviously so.

memory_limit is set to 24 GiB, deliberately below this machine's 36 GB. Set above the real cap, DuckDB never spills and the kernel kills the process — which is exactly how an earlier round produced a bogus "will not spill" finding.

Sorts are never forced with count(*), which lets the optimiser drop the ORDER BY; transforms are forced with sum(strlen(…)), because a transform projection under a count is discarded entirely and once reported 500k rows in 0 ms.

Row groups are counted, never derived. Dividing rows by 122,880 would have been wrong — DuckDB rounds — and inferring the unit is exactly the mistake that produced the per-file law this report retires. Where a measurement turned out to be an artifact of the bench rather than of the thing measured, it is excluded and said so, not quietly dropped.

What would invalidate it: real payloads whose row-group fill differs sharply from this corpus; a real S3 endpoint behaving unlike the model; or concurrency changing the memory picture. All three are in the next-steps list.
